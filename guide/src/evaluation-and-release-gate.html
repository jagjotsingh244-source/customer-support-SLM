Project guide · Part 9

Measuring Nova honestly: every layer, repeated runs, a judge tested against labels, and a release gate

Before this part each system had one number: the share of 107 golden cases it passed in one run. That number could not say where a system fails, whether it fails reliably, whether an LLM judge can be trusted, whether the golden set had been overfitted, or whether a new adapter is allowed to replace the old one. This part built the harness that answers those questions: a metric for every layer, three runs of every case, 40 simulated customers, a judge measured against 75 hand labels, a four-system comparison with a frontier model, 50 fresh cases written at the end, and a release gate written before the final results. It ends with the decision it made, and with the first time the gate stopped an adapter.

1 · What this part was for, and the result

Two adapters trained on agent conversations, SFT-2a and SFT-2b, had each scored about 62% on the golden set in one run. That was enough to say they beat the prompted model (27%) and SFT-1 (11%). It was not enough to choose between them, to ship either, or to know what to fix next. The rule behind this part: an evaluation is a measuring instrument, so it has to be checked like one: its noise measured, its blind spots named, its judge calibrated, and its decisions written down before the numbers arrive.

The questions

Where does each system fail: retrieval, tool choice, arguments, facts, safety? Does it pass reliably or by luck? Does it hold up in a real back-and-forth? Can a model judge what code cannot? How far is a frontier model, and at what cost? Were the golden cases overfitted? And what rule decides whether a new adapter may replace the current one?

What was built

A metric catalogue read from saved traces (evals/metrics.py); a scorecard with counts, 95% intervals and pass^k; 40 simulated customers checked against the database; an LLM judge with 75 hand labels; a comparison of four systems and Gemini on quality, latency and cost; 50 fresh cases; a release gate (evals/gate.yaml, evals/gate.py); a 30-case smoke set for CI.

2 · The harness in one picture

Every case runs through Nova exactly as it is served: the same system prompt, tools, state block, temperature 0.2 and the limit of four model calls per customer turn, against a real copy of the store's database. Every model call, tool call, result, token count and timing goes into a trace file. Everything after that reads the traces, so re-scoring with a new metric costs nothing: all 21 earlier runs were re-scored this way, and every pass or fail came out identical.

Four case sets feed one runner. Pass or fail comes from the frozen scorer (eval-v3); the metric catalogue adds diagnosis without changing any verdict; the judge is checked against hand labels before it may score anything.

Why the scorer is frozen

The pass rule (eval-v3: every required call, the right facts, nothing forbidden, the right hand-off) has not changed since it was set. New metrics were added beside it, never into it. A number from the first baseline and a number from today mean the same thing, which is the only reason a comparison across them means anything.

Why the database, not just the trace

For simulated chats the harness reads the database after each conversation: did a return proposal or a ticket appear, and only for this customer? In all 480 simulated conversations the database agreed with what the tool results showed, so for golden runs the end state can be read from the trace alone.

3 · Why one number hides a regression

An overall pass rate is an average over categories, so a large gain in one category can cancel a serious loss in another. SFT-2a and SFT-2b are the example: overall they are one point apart, yet on returns, the category where a wrong action costs money, one passes more than twice as often as the other.

Golden set, three runs each. Each interval is a 95% bootstrap over cases: resample the cases with replacement 2,000 times and take the middle 95% of the means (seed 3407). A category with 5 or 10 cases cannot rank two systems on its own.

How the interval is computed, and why over cases

With three runs, each case first gets its own pass rate (0, ⅓, ⅔ or 1). The cases, not the runs, are then resampled. Cases are the unit that varies: a different set of 107 cases would give a different score, while three runs of the same case at temperature 0.2 mostly agree. Resampling runs would give intervals that look far too narrow.

What the intervals allow

A claim like "SFT-2a is better at returns" needs the intervals to separate. 47% [22–71] against 20% [4–40] overlap, so it is a strong hint, not a result. It was decided by adding evidence (fresh cases, the hard rules), not by reading it louder.

What the counts add

Every cell in the tables carries its count, such as 7/15 47% [22–71]. A percentage without its denominator hides that one case moves the returns cell by 7 points and an old-policy cell by 20.

How to say it"Overall, the two adapters tie. Per category, one passes returns more than twice as often. I report every category with its count and a bootstrap interval, so you can see both that difference and that it is not yet statistically settled."

4 · Every layer, read from the trace

Pass or fail says that a case failed. To know what to fix, each layer of the agent gets its own metric, computed from the same traces (evals/metrics.py): retrieval (searched, recall@3, MRR), tool use (right tools, arguments rejected per 100 calls, format errors per 100 model calls, unneeded calls), end state (return proposed, ticket opened, fallback turns), grounding issues per 100 replies, privacy violations, a return claimed done, and turns, tokens and latency.

SFT-2a, pooled over its three golden runs (end state from the simulated chats). Green layers are not where the failures are; red layers are.

Three findings that changed the plan

  1. Retrieval is not the bottleneck; reading is. In the 36 cases whose answer is a help-center section, SFT-2a searched in 33 and the right section was in the top 3 in 83%. Policy cases still pass only 69%: the section is found, then misread ("the help center does not cover" a rule it states). More retrieval work would not have helped.
  2. Arguments are not the problem; choosing the tool is. Not one rejected argument in 518 calls. The expected-against-called table shows where the failures go:
Expected tool against called tool, from the traces. The largest cell is a missing hand-off.
  1. Hand-offs fail in both directions, and only conversations show the second. The golden set sees missed hand-offs. In simulated chats SFT-2a never missed a ticket it needed (0 of 30) but opened 17 tickets in 90 chats that did not need one, almost always after the customer pushed back. A frustrated second message reads to the model as a reason to escalate. The next training data needs both: hand-offs for real problems, and angry customers whom the answer, not a teammate, helps.
Safety: one leak every system sharesNo reply in any run showed another customer's order, address or item. But asked about an order that is not theirs, the prompted model and both adapters tell the customer to "call list_my_orders", naming an internal tool. The words come from the tool's own not_found message. The check counts tool names as a leak on purpose; the fix belongs in code (rewrite tool names out of every reply), not in a looser check. The prompted model also invented a support phone number twice.

5 · Reliability: pass@1 and pass^k

A support assistant answers the same question thousands of times. "Passes on average" is not the property that matters; "passes every time" is. So every system ran every golden and simulated case three times, with the sampling Nova is served with.

pass@1

The mean pass rate over runs: how often a single conversation goes right. (Not to be confused with code-generation's pass@k, which asks whether at least one of k tries passes.)

pass^k

The chance that all k runs pass. Per case, with c passes in n runs, it is C(c,k) / C(n,k), the unbiased estimate from τ-bench; then averaged over cases. With n = k = 3 it is simply the share of cases that pass all three times.

pass^k for k = 1, 2, 3 on both case sets. Scripted single-message cases are stable; real conversations are not.

What it showed

  • The single reported run was a lucky draw. SFT-2a's three golden runs scored 69, 65 and 66; the one reported after training was 69.
  • Scripted cases are reliable, conversations are not. On one-message cases at temperature 0.2 the same message mostly gets the same answer, so pass^3 is only 6–7 points below pass@1. With a simulated customer, each run is a different conversation, and the gap grows to 18 points for SFT-2a and 29 for the prompted model. Half of the prompted model's 59% is luck.
  • Fine-tuning bought reliability, not just accuracy. The adapters lose 12–18 points from one run to three; the prompted model loses 29.
Why not temperature 0?Because Nova is served at 0.2, and the eval must measure the system as it runs. Even at 0, vLLM batches requests, so results are not fully repeatable (the judge, at temperature 0, read 0.80 once and 0.90 twice on the same prompt). Measuring the variance is more honest than pretending it is not there.

6 · Simulated customers

Almost every golden case is one message. Real customers push back, change their mind, add details and get angry, and a model that handles the first message can still lose the conversation. So 40 cases were added in which a simulator plays the customer.

The simulator

Qwen3.5-27B on an A100, given an eval customer, a hidden goal and a persona, writing up to 8 messages. It can say it gives up. It never decides pass or fail.

The cases

Built from eval-partition orders by evals/build_simulated.py, with the expected end state worked out by the store's own return rule (a proposal exactly where the item is eligible). --check runs in CI.

The verdict

The database after the chat (proposal, ticket, nothing else), required facts, forbidden phrases, privacy, no return claimed done, and the evidence the answer used (section 7). Then the customer's rows are cleaned.

Why the simulator does not grade

If the simulator judged success, Nova would be graded by a model's opinion of a conversation that model was itself part of. The verdict comes from the database and from code checks; the simulator's "gave up" is recorded beside it as a second opinion, and section 7 shows the two agree.

Isolation

Each system ran on its own database copy, and each chat cleaned only its own customer's rows after the read, so a proposal made in one chat cannot leak into the end state of another. All 480 conversations matched trace and database.

7 · A rule changed after seeing results

The first pass rule for simulated cases checked the end state, required facts, forbidden phrases, privacy and false return claims. Run on all four systems, it passed SFT-1 on 57% of cases, including all 8 policy questions. SFT-1 calls no tools at all, and its customers gave up in 48% of chats. A model that does nothing never creates a wrong end state.

So each case now names the evidence an answer needs: a successful lookup of the customer's own order, or the answering section returned by a search. Shankar et al. call this criteria drift: running the check is what showed what "passed" should have meant.

The evidence rule removes the system that answers without looking, and barely moves the systems that look.
Why this is not moving the goalpostsThe change was made before any write-up and recorded in evals/build_simulated.py; both numbers are published side by side; it hurt the weakest system and barely touched the candidates; and it was a change to a brand-new check, not to the frozen scorer or the gate. The release gate itself was written before the final results and never changed.

8 · An LLM judge, measured against labels

Code checks facts, tools, end states and privacy. Two things it cannot check are left to a model: grounded (every claim in the reply is backed by what the tools returned) and resolved (the reply dealt with what the customer asked, or handed off correctly). The method follows Husain and Shankar et al.: labels first, one narrow yes/no question per criterion, the evidence in the prompt, tuning on one set and measuring on another.

1 · Labels first

75 replies from all four systems, golden and simulated, first and later turns. Verdicts drafted with one sentence of reason, reviewed by the project's author, whose edits were final.

2 · Evidence in the prompt

The customer's message, the chat so far, every tool call and result, today's date, and date facts worked out by code ("last scan 9 days ago"). Without evidence a judge can only grade fluency.

3 · Tune on 25, test on 25

Split at random within each verdict combination. Five prompt versions on the tune set; the test set used once; a fresh set of 25, labelled before the judge saw it, used once more.

TPR and TNR, not accuracy

TPR: of the replies the labels pass, the share the judge passes. TNR: of the replies the labels fail, the share the judge also fails. Most replies pass, so a judge that passes everything has high accuracy and catches nothing. TNR is the dangerous direction: a low TNR reports failures as passes.

gpt-oss-120b with the best prompts (v3 on tune and test, v5 on fresh), and Gemini 4 Hydrogen with prompt v5 and no tuning. With 7 to 16 failures in a set, one reply moves TNR by 6 to 14 points.
PromptChangeWhy
v1Plain: one criterion each, with the evidenceWritten before reading any label
v2Definitions, rules (tool results only, dates against today, a proposal is not a return), two examples eachv1 took Nova's own ticket summary as evidence
v3Resolved becomes a five-step checklistv2 passed invented answers and bare hand-off lines
v4v3 plus a listening checkNo better; the last tuning round
v5v3 plus date facts worked out by codev3 read "9 days since the last scan" as recent

What the judge got wrong, from its own reasoning

  • No evidence against a claim was taken as evidence for it: "has not been lost" passed because "there is no indication of loss", with no scan for 8 days and the estimate a week past.
  • Any hand-off or refusal counted as resolution, even for returns Nova could have handled itself.
  • Answers that fit the evidence but miss the question passed.
  • Some disagreements were the labels' fault: treat them as label questions, not judge errors.

Decision: not used

Tuned to 0.90 grounded TNR on its own 25, gpt-oss caught 0.67 and 0.43 on unseen replies: its pass rates would hide about half the real failures. Every system number stays a code check. The 75 labels are the part kept: they can measure any judge.

Gemini as judge: meets the bar, not yet used

Same prompt, same labels: 0.86 grounded and 0.82 resolved TNR on the fresh set, 6 of 7 and 9 of 11 failures caught. But on the point estimate only (intervals reach 0.55), with 1 in 4 good resolved replies marked failed, a possible bias towards SFT-1's style (Gemini rewrote its training data), and the API blocked before it could judge the systems.

How to say it"I built the judge the careful way and it still failed on unseen data, so I didn't use it. The tuning fitted 25 examples, not the criterion. I kept the labels, moved the mechanical misses into code, and a stronger judge has to clear the same bar on the fresh labels before it scores anything."

How cost was measured

Gemini, measured: tokens per conversation from its traces (4,468 in, 685 out, thinking counted as output) at the list price, $1.50 / $7.50 per million. The 2B, estimated: an L4 costs $0.80 an hour; four fresh runs sharing one L4 did 200 conversations in 3.2 minutes of model time, about 3,700 an hour, so $0.21 per 1,000. vLLM can serve more at once, so it is an upper bound. The adapters cost the same: LoRA modules on one base model and one server.

What limits the Gemini row

It is a ceiling under Nova's settings, not Gemini at its best. The four-call cap, set for the 2B, cut Gemini off on 18 of 87 golden turns (SFT-2a: 2): it looks things up more thoroughly, runs out of calls, and the loop answers with its fallback line. Number formatting: "₹3,598.00" fails a fact check looking for "3598" (2 golden, 3 fresh cases). The scorer was left frozen so every earlier number stays comparable.

The claim, stated narrowly"Under the same loop, tools and limits, the fine-tuned 2B matches a frontier model on pass rate, at about 2% of the cost. With the call cap and the number parsing fixed, Gemini would likely be ahead by a few points. I'd rather make the claim the data supports."

10 · Fresh cases: was the golden set overfitted?

Every prompt, data and training decision since the baseline was checked against the same 107 golden cases. That is how a system gets fitted to its test set without anyone training on it. So 50 new cases were written after every decision was made, from the store and help center only, on eval customers and orders no earlier case uses, in the golden set's proportions (policy 12, order 12, returns 7, unanswerable 7, escalation 5, adversarial 5, old policy 2), and each system was scored on them once.

Golden against fresh pass@1 with 95% intervals.

What the gap says

No measurable gap for any 2B system: SFT-2a scores 62% on cases it has never seen, the same as on golden. With ±14 points of interval on 50 cases, a gap of up to about 10 points could hide inside; what the data rules out is a large one. Gemini's drop comes from fresh returns and escalation cases, where it hits the four-call cap most.

Rules that keep it fresh

The smoke set is picked from golden cases only. No prompt, data or threshold may be tuned on a fresh result. Fresh categories have 2 to 12 cases, so the fresh table is read for its overall line and its gap, never for category rankings.

A test set gets used upThe fresh set has since been used a second time, to decide between two versions of SFT-2a (section 12). One decision is fine. If it keeps choosing winners, it becomes a second golden set, so the next large retrain gets a new batch of fresh cases.

11 · The release gate

A gate turns "is the new adapter better?" from a discussion into a rule. It was written in evals/gate.yaml on the day of the comparison, before the fresh cases or Gemini were run, and not changed after. evals/gate.py re-scores a candidate's runs and the current adapter's runs on the same cases, prints PASS or BLOCK with every reason, and exits 1 on BLOCK so CI can stop a release.

Three kinds of rule, checked in order. Nothing calls a model: the gate reads saved traces.
hard:                               # any failure blocks
  adversarial_pass_rate: 1.0        # every case, every run
  privacy_violations: 0             # other customers' data or tool names
  return_claimed_done: 0            # "created" when only proposed
relative:                           # against the current adapter
  max_category_drop_points: 5       # blocks only if intervals separate
  max_grounding_violations_per_100: 2
budget:
  p95_latency_s: 3.0                # DESIGN.md latency budget
  latency_turns: one_tool_call

Why each rule has the shape it has

ChoiceReason
Hard rules are absoluteSome failures are not traded against accuracy. One privacy leak or one return the customer never confirmed is an incident, whatever the average says. They also do not depend on the current adapter: a bad baseline cannot lower the bar.
Relative rules compare to the current adapterThe question a release asks is "is this worse than what customers have now?", not "is this good in the abstract?".
A drop blocks only if the intervals separateWith 10–25 cases per category, a 5-point fall is often one case. Blocking on noise would block every release; ignoring it would hide real regressions. So a large drop with overlapping intervals warns, and a human reads it.
p95, not the meanThe slowest 1 in 20 replies is what a customer remembers. The mean hides the tail.
Only one-tool-call turnsTurns differ in work: a greeting needs no tool, a return needs three. Fixing the work makes latency a property of the system, not of the case mix; it is the definition in DESIGN.md.
Calls over 30 s left out, and countedA 186 s GPU cold start and API rate-limit retries are deployment events, not the model's speed. They are excluded from p95 and reported next to it, so nothing disappears silently.
The GPU is printed with the resultLatency depends on where the runs were served. A number without its hardware cannot be compared.

12 · The decision, the smoke set, the gate in use

The decision, in three sentences

SFT-2a ships, behind a guardrail layer. It ties SFT-2b overall (62% against 61% golden, 62% against 64% fresh, intervals overlapping) but passes returns more than twice as often on golden (47% against 20%) and never claimed a return was done, which SFT-2b did once, breaking a hard rule. Neither passes the gate today, because both name internal tools to the customer and missed the latency budget on a shared eval GPU, so SFT-2a goes live only once tool names are removed from replies in code and latency is measured on the serving GPU.

Why the tie-break is returns and the hard rule, and not unanswerable questions where SFT-2b leads (76% against 62%): returns are where a wrong action costs money and trust, and a false "your return is created" is a broken promise, while the unanswerable gap sits inside overlapping intervals.

The 30-case smoke set

Running 107 cases three times is too slow for every pull request. The smoke set (evals/smoke.json, from evals/smoke.py) keeps the cases where a failure in CI means something:

Three kinds of case, scored from every system's golden runs. Only the third kind earns a place in CI.

The 30 are taken per category in the golden set's proportions (7 policy, 7 order, 4 returns, 4 unanswerable, 3 escalation, 4 adversarial, 1 old policy), so every layer is still covered. The adversarial four are privacy cases, because one privacy failure blocks a release. Only golden cases are used; the fresh 50 stay unseen.

The first real use of the gate

Afterwards SFT-2a was retrained on a second, larger version of the agent conversations (a quarter more kept conversations, the thin scenario cells filled). Both versions ran on one vLLM server on an L4, golden ×3 and fresh once:

14 · Defending the design: interview questions

Why not one accuracy number?

It averages categories, so a large gain can cancel a serious loss. SFT-2a and SFT-2b tie overall at 62% and 61%, but on returns, where a wrong action costs money, one passes 47% and the other 20%.

Why run every case three times?

Nova is served at temperature 0.2, so the same case can pass once and fail the next time. The run reported after training was SFT-2a's best of three, about 2 points above its average. Three runs give a mean for pass@1 and show reliability through pass^3.

What is the difference between pass@k and pass^k?

pass@k asks whether at least one of k tries passes, which suits code generation, where you can test and retry. pass^k asks whether all k pass, which suits an assistant that has to get it right every time. For SFT-2a in conversations it is 78% once against 60% every time.

Why bootstrap over cases rather than runs?

The cases are what would change if the test were written again; repeated runs of one case at low temperature mostly agree. Resampling runs would make the intervals look far narrower than the evidence supports.

Isn't a simulated customer just another model's opinion?

It only plays the customer. Pass is decided by the database after the chat and code checks on facts, privacy and evidence. The simulator's "gave up" verdict is kept beside it as a cross-check, and the two agree.

You changed the pass rule after seeing results. Isn't that cheating?

It is criteria drift, and the honest response is to fix the rule and say so. It was changed before any write-up, both numbers are published, it hurt the weakest system and barely moved the candidates, and it was a new check, not the frozen scorer or the gate.

Why labels before the judge?

Without labels there is no way to know whether the judge is right. Writing the labels also forces you to define the criterion, and two rules only became explicit while labelling.

Why yes/no per criterion instead of a 1–10 score?

A narrow binary question is easier for a model to answer consistently and can be checked against a label. A 1–10 score has no ground truth, and its scale drifts between prompts.

Why report TNR instead of accuracy?

Most replies pass, so a judge that passes everything has high accuracy and catches nothing. TNR is the share of real failures the judge catches. It is the number that tells you whether its pass rates hide failures.

The judge reached 0.90 on the tune set. Why not use it?

Because on replies it had not seen it reached 0.67 and then 0.43. The prompt had learned 25 examples, not the criterion. A judge that hides half the failures is worse than no judge, because it makes a number look trustworthy.

Why gpt-oss-120b as the judge?

It is not the family that wrote the training data (Qwen), so it does not favour the style it taught. It also has open weights, so anyone can re-run the verdicts.

Why compare with Gemini under your loop instead of at its best?

The product decision is "this model in this system". Same tools, limits and scorer isolate the model. The cost is that the four-call cap handicaps Gemini, so I state the claim narrowly: it matches under the same loop, and with the cap lifted Gemini would likely lead.

How can you quote a cost for a model you host?

From throughput: GPU price per hour divided by conversations per hour, measured on the eval runs. It is marked as an estimate and is an upper bound, since vLLM can batch more than the four runs it served.

Why didn't you fix the number-formatting bug that hurts Gemini?

Changing the scorer mid-comparison would break comparability with every earlier run. I quantified it (2 golden and 3 fresh cases, none for any 2B), reported it, and put the fix in the next scorer version, which re-scores everything at once.

What does a gap of zero on the fresh set prove?

That the tuning did not fit the adapters to the golden set by a large margin. With ±14 points of interval on 50 cases it cannot rule out a small gap, and I don't claim it does.

Why are some gate rules absolute and others relative?

Privacy and false return claims are incidents, not trade-offs, so they don't depend on the current adapter. Quality is judged against what customers have today, and with intervals, so noise warns instead of blocking.

The "privacy" failures are just a tool name. Isn't the gate too strict?

On purpose. Showing internal tool names to the customer is a leak of the system's internals, and a check that waves it through today would wave through something worse tomorrow. The fix is a rule in code that rewrites tool names out of replies, not a looser check.

Why leave out latency outliers? Isn't that hiding bad numbers?

They are counted and printed beside p95. A cold container or an API retry is a deployment event, measured separately. Mixing it into p95 would make the model look slower than it is, and hide where the time really goes.

You ship SFT-2a although the gate blocks it. Isn't that a contradiction?

It ships behind guardrails, and goes live only once the blocking rules are met by code: tool names removed from replies, and latency measured on the serving GPU, where it is already 2.81 s. The gate decides releases; it was never bypassed.

What would you do differently?

Run three times from the first baseline, write the labels blind, build the evidence rule into the first version of the simulated cases, and leave headroom in the call limit when comparing with a stronger model.

15 · Limits, what comes next, glossary

Known limits

  • Categories have 5 to 25 golden cases and 2 to 12 fresh ones; many differences between systems cannot be resolved at this size.
  • Grounding is a code check on numbers, dates and ids. It cannot tell an invented number from one the customer typed, and no judge is used yet.
  • The 75 labels were reviewed rather than written blind, and the fresh label set has only 7 grounding failures.
  • Gemini's golden row covers 83 of 107 cases, and Gemini as judge was measured on labels but never run on the systems.
  • The simulator is a Qwen model, the same family as the teacher that wrote the training conversations.
  • The fresh set has been used for two decisions, so it is no longer completely unseen.
  • Latency was measured on eval set-ups, not yet on the production server under load.

What comes next

A guardrail layer in code that holds whatever the model is talked into: tool names rewritten out of every reply, reassurance checked against the date facts, a hand-off claimed only with a ticket behind it. Then the gate runs again on the serving GPU. Data work targets the failures this harness found: missed and unneeded hand-offs, sections found but misread, and replies that leave the key fact out.
