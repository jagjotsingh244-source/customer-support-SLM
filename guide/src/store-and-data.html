1 · Why build the world first

The tempting order is to generate chat data and start training. The problem shows up later: synthetic chats say an order is "Dispatched", but the database says shipped, so the model learns words its tools never return. A customer whose order came in two boxes asks where the second one is, and there is nothing to look up because the table holds one tracking number per order. The model was never wrong; the world it was trained on did not exist.

So the store came first. Every later part of the project reads from it:

The schema is treated like a public API: a contract that everything downstream depends on.

What exists now

Store data

500 customers, 60 products, 3,000 orders, 3,048 shipments, 4,575 order lines, 9,257 tracking events, 270 returns, 230 refunds, 132 tickets, 2,795 payment attempts.

Rules written down

11 store tables and 9 enums, 6 state machines, 19 invariants, one frozen clock and a hash-based train/eval split.

Knowledge and proof

18 help-center pages (103 searchable sections), 16 customer questions with tested SQL, and a CI workflow that rebuilds and checks everything on every push.

How I'd say it in an interview"I treated the database as the contract. The tools, the training data and the evals are all derived from it, so I designed it first, from the questions customers actually ask, and made bad data impossible to insert."

2 · Designing from customer questions

Martin Kleppmann's advice in Designing Data-Intensive Applications is to model data around how it will be read. Nova reads the store to answer customers, so the design went backwards from their questions:

The 16 questions

3 · The schema and its rules

Eleven store tables plus one metadata table (db/schema.sql, re-runnable). Arrows point from a table to the table its foreign key references.

Why order_items.shipment_id matters: a split order has two boxes, and each line records the box it travels in, so "where is the second box?" has an answer.

Six rules, and why each exists

RuleWhyExample in the schema
Every status is an enumFree-text statuses produce free-text answers. A fixed list is also what the tools return and what training data must use. order_status has exactly 8 values; inserting 'in transit' fails.
Money is NUMERIC, never FLOATFloats drift by paise, so a refund total that is "correct" fails an exact eval check for no visible reason. NUMERIC(10,2) for every ₹ amount; positive checks on prices.
Store every timestamp a "when" question needs"When" questions are the most common kind. If a time is not stored, the model guesses it. placed, shipped, ETA, delivered, scans, proposed, confirmed, picked up, refunded, rejected.
Status and its timestamp agreeA status without its time (or a time without its status) is a contradiction the model would repeat. CHECK ((status = 'cancelled') = (cancelled_at IS NOT NULL)), the same for delivered, rejected, completed, resolved, reversed.
No free-text notesA notes field is where prompt injections hide ("ignore your instructions…"), and no tool can check it. Reasons are enums: return_reason, rejection_reason, ticket_reason.
Foreign keys everywhere, composite where neededA row pointing at nothing is a fact Nova could state that is not true. return_items references both returns(return_id, order_id) and order_items(order_id, line_no), so a line from order A cannot go into a return for order B.

db/break.sql loads valid fixtures, then tries ten inserts that break a rule. CI counts the errors and fails unless there are exactly 10. Everything runs inside one transaction and is rolled back, so the seeded data is untouched.

Indexes follow the access pattern: every tool looks up by customer or by order, so there are indexes on orders(customer_id, placed_at), shipments(order_id), shipment_events(shipment_id, at) and the other lookup columns.

4 · State machines: allowed moves

An enum says which statuses exist. A state machine says which status may follow which. db/STATES.md lists every allowed move for orders, shipments, returns, refunds, tickets and payments; anything not listed is forbidden, such as delivered → packed.

The order state machine. Thick borders mark terminal states. Only two moves belong to Nova: cancelling, and confirming a return.

Rules that tie an order to its boxes

  • An order follows its least advanced box. One box delivered and one in transit means the order is shipped, not delivered.
  • A cancelled order stays cancelled. Its money is tracked in refunds; refunded means "refunded after a return".
  • "Possible loss" is computed, not stored. No scan for 7 days is a question about time, so it is worked out from the last event and NOW. The status lost means the carrier confirmed it.
  • Cancelling a packed order voids its labels (shipment label_created → cancelled), so the order can still show its tracking number. This was found while writing the state machine: without it, the label had nowhere to go.

Money decisions, written down

SituationDecision
Cancellation refundThe full order total, shipping included.
Return refundThe returned items only; the shipping charge is not refunded. A check enforces refund = value of the returned lines.
COD returnThe refund row is created at inspection as awaiting_bank_details; the return becomes refunded only once bank details are added.
Failed payment that took moneyA payment reversal (5–7 business days), never a refund. Refunds are only for successful payments.

Three kinds of rule, three places

Schema CHECK

One row, at insert time.
"A cancelled order has a cancelled_at." Postgres refuses the row.

State machine

One row, over time.
"delivered → packed is not allowed." Written in STATES.md; the tool layer only makes Nova's two moves.

Invariant

Many rows, in one snapshot.
"A delivered order has no undelivered box." A query in checks.sql that must return zero rows.

Not built, on purpose: a BEFORE UPDATE trigger that looks up (OLD.status, NEW.status) in an allowed-moves table would make Postgres enforce the state machine itself. The seed inserts final states and never updates, so it adds nothing yet; it is the first thing to add if real updates arrive.

5 · One clock and two worlds

Two cheap fixes made early, both painful to add late.

The clock is frozen

Return windows, "late by three days", "arriving tomorrow" and refund timelines all depend on today's date. If the seed or the checks read the real clock, a correct eval case silently becomes wrong as weeks pass:

So there is one clock: config.NOW, read only through now(). The seed, the system prompt ("Today is 20 November 2026"), every eligibility check and every eval use it, and SQL receives it as a parameter (:'now'), never now(). In production, now() is the single line that switches to real time.

NOW = datetime(2026, 11, 20, 10, 0, tzinfo=IST)   # frozen for development and evals

def now() -> datetime:
    """The only way any code in this repo asks for the time."""
    return NOW

Enforced, not hoped for: scripts/check_clock.sh runs in CI and fails if any Python outside config.py calls datetime.now(), date.today() and similar, or any SQL uses now(), current_date, current_timestamp or the other clock functions. It caught a comment I had written myself on its first run.

The world is split in two

  • Why split by customer, not by order. Split by order, one customer's orders land on both sides, so training chats describe the very people the eval asks about. The eval would partly measure memory.
  • Why a hash, not a random draw. A customer's side never changes, even if the seed adds customers or the generation order changes. It is sha256, not Python's hash(), which is salted per process for strings.
  • Why the help center can be shared. Policies are retrieved at answer time, so seeing a policy in training doesn't leak an eval answer. Order facts are per customer and come from tools; those are what the split protects.
  • The cost of a hash: the split came out at 17.6% eval, not 20%. That is fine; a stable side matters more than an exact share.
How I'd say it in an interview"It's the train/test split from classic ML, applied to a database instead of a CSV, and keyed on the entity that could leak: the customer. Kapoor and Narayanan's paper on leakage in ML-based science is the reason I took it seriously."

6 · Seeding the hard cases

A realistic average day would be useless: real stores have very few lost parcels, so an eval would contain almost none and training would never teach them. db/seed.py builds the store from 15 scenarios, each a path through the state machines stopped at a chosen point relative to NOW. 870 orders (29%) are deliberate hard cases.

Orders per scenario (exact counts, shuffled). Every scenario has at least 7 orders on eval customers; the seed tops up any scenario that falls below 5 and a check fails the build if one is still short.

How a scenario is built

Each scenario has one builder function. A builder starts from a past "today" and walks forward through the real steps, so every timestamp is consistent with the ones before it. Every timestamp goes through one helper that asserts it is before NOW: a builder that asks for the future crashes instead of writing a bad row.

# the delayed scenario, in outline
placed   = ago(days)                          # in the past, before NOW
shipped  = later(placed, hours=…)             # forward from the last step
eta      = shipped + transit_days(city)       # metro 2–4 days, other 4–7
scan(box, hubs…)                              # tracking events, all < NOW
# stop here: ETA has passed, the box is still in transit, last scan recent

Choices that make the seed trustworthy

ChoiceWhy
Deterministic: one seed (3407) for Python's RNG and Faker's en_IN localeTwo runs produce identical databases (checked by diffing two pg_dumps), so an eval case written today points at the same rows next month.
Exact counts, then shuffledShares like 3% become exactly 90 orders, not "about 90", so per-scenario scores always have the same denominators.
Order IDs follow timeDrafts are sorted by placed_at before IDs are assigned, as in a real store, so a newer order never has a smaller ID.
Policy numbers are named constantsReturn windows, transit days, refund days and the ₹499 free-shipping line live in one place, so the help center and the return check can be compared against them.
Indian detailsPrices in ₹, UPI/card/wallet/COD, 8 metro and 16 other cities with valid 6-digit pincodes, two carriers with distinct tracking prefixes.
A scenarios tableEvals and the training-data sampler need to know which situation an order was built from. Nova's tools must never see it: it would hand the model the answer.

19 invariants, zero rows each

db/checks.sql holds one query per rule that spans rows or tables. The seed runs them all after loading and exits non-zero if any returns a row. Grouped:

Time

Nothing after NOW; no order before its customer existed; no box shipped before its order was placed, or delivered before it shipped; no tracking event outside shipped–delivered; no return proposed before its item was delivered.

Money

Total = items + shipping fee; the fee follows the rule (free above ₹499, else ₹49); no refund above what was paid; a return refund equals the value of the returned lines.

Status agreement

Order status follows its least advanced box; a delivered order has no undelivered box; a cancelled order has only voided boxes; a carrier-held box has a ship time and ETA; a shipped item is in a box; return statuses match the order's.

Coverage

Only electronics and hygiene items can be marked opened; every order has a scenario; every scenario has at least 5 eval orders.

Testing the testsAll 19 checks passed on the first run, which proves nothing on its own. So I broke five things on purpose (a total off by 1 paisa, an opened home item, a tracking scan in the future, a split order marked delivered while one box was in transit, and every eval customer moved to train); the checks caught all five. A check that has never failed is not yet known to work.

7 · A help center written for retrieval

Nova answers policy questions from retrieved help-center text, and a 2B model copies what it retrieves. So the 18 pages in kb/ were written for a retriever and a checker as much as for a reader.

Writing ruleWhyBad → good
One topic per page, one rule per ## sectionEach section becomes one retrievable chunk; a mixed chunk retrieves the wrong rule alongside the right one."Returns" (everything) → "Returning electronics", "Items you cannot return"
Every number in digits, with its unitAn answer can be checked by matching digits; a vague phrase invites the model to invent a number."about a week" → "within 7 days of delivery"
The exception sits next to its ruleIf the exception is on another page, retrieval returns the rule alone and Nova states it wrongly."Opened electronics can be returned only if they are faulty" in the electronics page
One term per ideaSynonyms split retrieval and confuse the model about whether two things differ."parcel / package / box" → "shipment"; "working days" → "business days"
Plain, not marketingNova copies the style of what it retrieves."Hassle-free returns!" → "You can return… within 15 days"
Front matter on every pageRetrieval and citations need an id, a version and an effective date.policy_version: 2, effective_date: 2026-10-01

The help center is checked against the seed

scripts/check_kb.py runs in CI. It checks front matter, the 600-word limit and at least two sections per page, and flags vague timings ("soon", "a few", "a week"), numbers in words ("seven days") and banned synonyms. Then the important part: it builds the facts each page must state from the seed's own constants (for example f"within {WINDOW_DAYS['home']} days of delivery") and fails if a page doesn't say them. Change a window in code and the page that promises the old one fails the build. Five planted mistakes were all caught, including a page that no longer matched the 15-day window.

Three supporting files

  • kb/_archive/returns-general-v1.md: an older 30-day returns page, never indexed. It tests later that Nova cites the current rule, not an old one that sounds plausible.
  • kb/_customer_words.md: how customers phrase things ("money back", "parcel", "didn't get it"), to test that retrieval finds the right page when the customer's words differ from the page's.
  • Language scope: English, including Indian English. Hinglish has no training data yet, so it appears only as an unscored probe that measures the gap and never counts in a score.
A detail interviewers like"7 days" means three different things across the pages: the electronics return window, the no-scan time before a parcel counts as possibly lost, and the time to report a faulty non-returnable item. Each is stated with what it counts from, so retrieval can't swap them.

8 · Proving it: five layers of checks

Each layer catches a different kind of mistake, and every one runs in CI on every push.

The query gate

The 16 queries live in one file, db/questions.sql, first tested on a small hand-built world (db/fixtures.sql: one customer with one order per question). db/verify_queries.py then reads the same SQL from that file, so the tested queries and the checked queries can't drift apart, and runs it against the full store:

  • Each of 24 cases pairs a question with a scenario and runs it for every eval order of that scenario, about 1,100 query runs. Example: Q2 on every delayed order must report "late, ETA passed, not yet a possible loss"; on every lost order it must report a possible loss; on every on-time in_transit order it must report nothing late.
  • The answer is compared with what the scenario's builder made, read straight from the tables.
  • Scope check: Q1 is asked for each of the 521 eval orders by a different customer, and must return zero rows every time. Every query has customer_id = :cid in its WHERE clause, even when an order ID is given.
  • Proof it can fail: changing one row's ETA made exactly that order's case fail.

What CI runs on every push

Run by hand: uv run python -m db.seed, uv run python db/verify_queries.py, psql "$DB_URL" -f db/break.sql, uv run python scripts/check_kb.py, bash scripts/check_clock.sh.

9 · Bugs and surprises worth telling

These are the stories that show the checks earning their place. Each is symptom → cause → fix.

SymptomCauseFix
Dates could be a day off for early-morning timesThe Docker Postgres runs in UTC, and ::date uses the session time zone, so anything between 00:00 and 05:30 IST landed on the previous day. Every query session sets TIME ZONE 'Asia/Kolkata'; verified that IST and UTC sessions now give identical output. The tool layer does the same.
"Can I cancel?" had nothing to look upCounting order statuses before the gate showed zero placed or packed orders: no scenario stopped before shipping. Added a not_yet_shipped scenario (3%). Takeaway: check every question has seeded rows behind it as soon as the scenarios are listed.
A packed order, once cancelled, kept a live shipping labelThe shipment state machine had no exit from label_created. Added shipment status cancelled; a check fails if a cancelled order has an unvoided box.
My own test data broke the splitThe hand-built fixtures marked customer 1 as train; the hash says eval. Fixtures follow partition_for. Even careful hand-written data broke a rule straight away, which is why the rules are checked by code.
The help-center checker misread amounts with a thousands comma (₹1,499)Inside a Python f-string, the regex quantifier {3} silently became the literal 3. Escaped as {{3}}, so amounts with a comma are read whole.
Two "identical" seeds produced different dumpspg_dump writes a random \restrict token in each dump. Compare with those lines excluded: the data is identical.
Sealed earbuds were marked not returnableThe data treated hygiene items as never returnable, while the help center said "once unsealed". Kept the help center's rule (sealed follows the normal window); the return check, the SQL, the seed and the wording now agree. Recorded in the design log.
The clock guard failed on its first runA comment in questions.sql mentioned the clock function by name. Reworded it. Writing the guard before the code it protects pays off immediately.
If asked "tell me about a hard bug""The time-zone one. Nothing errored: queries ran and returned dates. But ::date depends on the session time zone, and the Docker image defaults to UTC, so an order delivered at 2 a.m. IST showed the previous day. A return-window answer could be wrong by a day, which is exactly the kind of error a customer notices. I set the session zone explicitly and checked the output is identical whichever zone the server uses."

10 · Defending the design: interview questions

Why design the database before generating any training data?

Because the training data, the tool schemas and the eval cases are all derived from it. If the chats say "Dispatched" and the tool returns shipped, the model learns vocabulary its tools never use. Designing from 16 real questions found 13 gaps on paper, when each fix was a line of SQL rather than a regenerated dataset.

Why enums instead of text statuses?

A fixed list is a contract: the tool returns one of 8 values, training data uses the same 8, and an eval can compare exactly. Postgres refuses anything else at insert time, so a typo can't become a "ninth status" Nova has to explain.

Why does each order line point at a shipment?

Split shipments are common. With one tracking number per order, "where is my second box?" has no answer. Linking each line to its box also makes return windows correct: the window counts from the delivery of that item's box, not the order's first delivery.

Why copy the address onto each order?

An order ships to the address it was placed with. If it only lived on the customer profile, editing the profile would silently "move" orders already in transit, and Nova would report the wrong destination.

Why freeze the clock? Isn't the real time more realistic?

Eligibility depends on dates. With the real clock, an eval case that is correct today becomes wrong in a month with no code change, and you can't tell drift from regression. A frozen NOW makes every date answer reproducible. Production switches one function to real time, and a CI guard makes sure nothing else reads the clock.

Why split by customer, and why a hash?

Splitting by order puts the same customer on both sides, so the eval partly tests memory of training chats. Hashing the ID keeps a customer's side fixed forever, even when the seed grows; a random draw would reshuffle. The price is 17.6% eval instead of exactly 20%.

Real stores have far fewer problems. Why seed 29% hard cases?

Evals and training both need enough examples of each failure mode to measure and to learn. At a realistic 0.5% lost-parcel rate, the eval would have two lost parcels and the score for that behaviour would be noise. Scores are reported per scenario, so the skew doesn't distort an average.

How do you know the generated data is correct?

Five layers: schema constraints refuse bad rows (10 bad inserts fail), 19 invariants check cross-table rules after every seed, the query gate runs the real SQL on every eval order, the help center is checked against the seed's constants, and two seeds are compared for identical output. Each checker was also tested by planting failures, because a check that has never failed isn't known to work.

Why isn't the state machine enforced by a trigger?

It could be: a BEFORE UPDATE trigger checking (OLD.status, NEW.status) against an allowed-moves table. The seed only inserts final states, so a trigger would never fire. Nova's only two writes go through the tool layer, which checks eligibility. Once real updates exist, the trigger is the first thing I'd add.

Why is every query filtered by customer, even with an order ID?

"Only show customers their own orders" must hold every time, so it is enforced in code, not left to the prompt. A customer who types someone else's order number gets "not found". The gate proves it on all 521 eval orders.

Why check the help center with code?

Because the most damaging bug in support is a page that disagrees with the system, such as 10 days on the page and 7 in the eligibility check. The checker builds the required sentences from the same constants the seed uses, so the two can't drift silently.

What would change at real scale?

Real time in now(); the state machine enforced in the database; tracking events arriving from carriers instead of a seed; the eval set built from anonymised real conversations alongside the synthetic one, still split by customer; and monitoring for which help-center pages lead to escalations, so those pages get rewritten first.

11 · Limits, what comes next, glossary

Deliberately not modelled

  • Cancelling after shipping. Free cancellation ends when the order ships; after that the routes are refusing delivery or a return.
  • How a lost parcel ends. The lost scenario stops while support is investigating.
  • A second return on one order. One return per order keeps the world simple; revisit if a scenario needs it.
  • Distribution realism. Synthetic names, prices and timings come from Faker and uniform ranges, so the data is consistent but smoother than reality. It is built to test behaviour, not to model demand.

What comes next on this foundation

  • Golden eval cases written against eval customers, with every expected fact read from these tables or a help-center page.
  • The help center in Postgres as 103 searchable sections, the starting point for retrieval.
  • A managed copy for GPU notebooks. The local Docker database stays the source of truth; a copy on Neon (same Postgres 16 and pgvector) was checked for matching row counts, byte-identical orders and a 24/24 query gate.
