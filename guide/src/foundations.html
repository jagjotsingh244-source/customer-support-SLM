1 · The project in one page

Nova is the support assistant for NimbusCart, a made-up Indian online store (prices in ₹). Customers ask the questions every store gets: where is my order, can I return this, when do I get my refund, why is it late. Nova answers from the store's real data and the current help center, and hands off to a human when it should.

It is built on Qwen3.5-2B, a small open model, fine-tuned with LoRA, served with vLLM, and surrounded by code: a tool layer over Postgres, retrieval over the help center, guardrails and an eval harness.

Why build it this way

The common approach is to send every question to a large hosted model with a long prompt. For a narrow job like support that is expensive per conversation, slow, and hard to control. The bet here is that a small model plus the right surrounding system does the narrow job better:

  • facts come from documents and the database, not from the model's memory;
  • behaviour (tone, when to call a tool, when to escalate) is trained into the model;
  • rules that must never break are enforced in code, whatever the model says.

2 · Where each capability lives

There are four ways to give a model a capability: write it in the prompt, retrieve it (RAG), fetch it with a tool, or fine-tune it in. A fifth option, code, takes the decision away from the model entirely. Choosing wrongly is the most common failure in LLM products, so the choice is written down per capability.

The four rules

RAG If it changes often, retrieve it

Policies, shipping charges, warranty terms. Updating a document is an edit; updating weights is a training run. The answer can cite the current text.

Tool If it belongs to one customer, fetch it

Orders, tracking, refunds, returns. This data is live and private; it can never be in the weights or the help center.

Fine-tune If it describes how to act, train it

Tone, one question at a time, calling the right tool before talking about an order, escalating after two failed turns.

Code If it is a hard rule, enforce it in code

Who may see which order, whether a return is eligible, what counts as a confirmed write. A prompt is followed "most of the time"; these must hold every time.

The rules as a decision flow

A capability can pass through more than one box: "start a return" is a tool, its eligibility check is code, and the confirm-then-act conversation is trained.

The capability map

Why most rows use two or three mechanisms

Each mechanism answers a different question. A tool supplies the data, but something has to make the model call it at the right moment: that is fine-tuning. And when the stakes are high, code double-checks the result. "Start a return" needs all three: the tool does the write, code decides eligibility, training teaches the confirm-then-act conversation.

One decision worth defending: escalation is trained, not counted

"Escalate after two failed turns" could be a code counter. It is trained instead, because deciding whether a turn failed needs understanding the conversation: a code counter cannot tell "thanks, that helps" from "that's not what I asked". The decision is recorded in DESIGN.md with a trigger to revisit it if evals show missed escalations.

Say it "Every capability has a mechanism and a measurement. Anything that must hold 100% of the time is code, because a prompt or a fine-tune only shifts probabilities. Rows enforced in code must pass 100%; the other pass marks are placeholders until the baseline eval shows what is realistic."

3 · Budgets: numbers before code

Budgets were set before anything was built, so every later decision (prompt length, number of retrieved chunks, model size, GPU choice) can be checked against a number instead of a feeling. Each number is labelled as a target (a product requirement), an estimate (a guess to replace) or a measurement. Every change goes in the change log with the old value, the new value and the evidence.

BudgetValueReasoning
p95 latency, reply with one tool call3 s targetCovers two model passes (emit the tool call, then answer from the result) plus the DB query. p95, not average, because the slow replies are the ones customers notice.
Context window8,192 tokens targetOur limit, set with vLLM's --max-model-len; the model itself supports far more (about 262K). Smaller context means less GPU memory per conversation, faster prefill, and better accuracy for a 2B model, which loses facts buried in long prompts.
Max size of one user message1,500 tokens target, codeAbout 1,100 words. Over the cap there is no model call, only a fixed polite reply. Stops one paste from eating the history budget, slowing prefill or hiding an injection.
Cost per 1,000 conversations~$5 estimateAssumes a GPU at about $1/hour serving about 200 conversations/hour. To be replaced with the real GPU rate and measured throughput.

How the 8,192-token window is split

When a prompt is still too long: trim the oldest history first, then retrieved chunks; never the system prompt or the tool schemas, because without them the model loses its rules and its tools.

Why set budgets this early

  • They turn arguments into arithmetic. "Can we add a seventh tool?" becomes "each tool costs about 80 tokens; 700 leaves room for one more".
  • They drive model and hardware choice. A 3-second p95 rules out slow engines; that is why Transformers (13 s for one reply on a T4) can't serve Nova.
  • They keep honesty. An estimate is labelled as one until a measurement replaces it, and the change log shows the evidence.

What the first measurements say

The tool-schema estimate (700) was measured at 656 tokens for six draft tools: about 180 fixed plus about 80 per tool. Later, the first end-to-end latency measurement of the prompted model (vLLM on one T4, database on managed Postgres) gave model passes of about 1.0–1.5 s each when warm, so a one-tool-call reply sits near 2 s, inside the target. A turn that needs two tool calls measured median 3.10 s and p95 3.60 s, over the target: a known gap, recorded rather than hidden.

Say it "I wrote budgets before code and labelled each one as a target, an estimate or a measurement. When a measurement replaces an estimate, the change log records old value, new value and evidence. That's how I know two-tool-call turns are currently over the 3-second target and one-tool turns are inside it."

4 · Why Qwen3.5-2B

The model was chosen for the job, then tested on the actual hardware before any further work depended on it.

ReasonEvidence
Fits a free 16 GB T4About 4.5 GB of weights in 16-bit. LoRA training at full 16-bit precision ran 50 steps in 165 s. A 7–8B model would need 4-bit quantisation just to train on a T4.
Fast enough for 3 s50 tokens/s in vLLM on a T4: a typical 128-token reply in 2.6 s. A model four times larger is roughly four times slower and costlier.
Calls tools before any trainingThe base model answered "Where is my order 4417?" with a correct get_order_status call. Fine-tuning only has to teach the harder cases: no order number, several orders, when not to call.
Non-thinking modeOne model, with reasoning switched off by the prompt. Thinking added 3–11× tokens and time with no better answer on lookup turns (section 7).
Open license and tool supportOpen weights (Apache 2.0), supported by Transformers, Unsloth and vLLM: exactly what the risk tests checked.

Alternatives considered

ModelWhy not first choice
Qwen3-1.7B / Qwen3-4BThe pre-agreed fallbacks: text-only, older, very well supported. Would have been used if the risk tests had failed.
Llama 3.2 3BSolid, but weaker built-in tool calling and a more restrictive license.
7–8B modelsBetter raw quality, but 4-bit training on a T4 and about 4× slower serving, which breaks the latency and cost budgets.

Honest trade-offs

  • A 2B model is less reliable. It follows long instructions loosely and invents answers more readily, which is why behaviour is trained and hard rules are code.
  • The architecture is new. Qwen3.5 mixes Gated DeltaNet (linear-attention) layers with full attention. Tooling is less mature: Transformers falls back to slow reference kernels (11 tok/s on a T4), and vLLM needed a fix to start (section 8).
Say it "I picked the smallest current model that already calls tools, runs inside my latency budget on a free GPU, and can be trained and served for free. The cost of a 2B model is reliability, so I compensate with retrieval, tools, fine-tuning and code-enforced rules, and I measure it with a baseline eval before training."

5 · Training on free GPUs that disconnect

Training runs on free Kaggle and Colab T4s. Both end sessions: idle timeouts, quotas, closed tabs. A notebook's disk is wiped when the session ends. So the setup is designed around one assumption: the machine will disappear mid-run.

The design: stateless notebooks

Code comes from Git

The notebook only logs in, clones the repo, installs the pinned versions, loads a YAML config, sets the seed and calls training/train.py. No training logic lives in a notebook.

Data comes from the Hub

Datasets load from Hugging Face, so a fresh machine gets the same rows.

Checkpoints go to the Hub

hub_strategy="checkpoint" pushes every save to a private model repo's last-checkpoint folder. LoRA keeps checkpoints a few MB, so pushes are fast.

Settings live in YAML, with a fixed seed

Same config + same seed = comparable runs. Secrets come only from the platform's secrets panel, never from cells or the repo.

Illustration with example step numbers: saves every 50 steps mean a crash loses at most 50 steps of work.

Resuming is one flag: --resume downloads last-checkpoint/ from the Hub (snapshot_download) and calls trainer.train(resume_from_checkpoint=...), which restores the weights, optimizer state and step counter.

Proving it: the disconnect drill

A tiny model (SmolLM2-135M, 300 steps, save every 50) was trained on Colab, the runtime was deleted mid-run, and a new session resumed from the Hub.

What went wrong, and the fix The first drill resumed from step 250, not around 100 as planned. The tiny model trained faster than the runtime could be deleted by hand, so the newest save was already at 250. The resume itself worked; the test didn't test what it meant to. Fix: a pause_at_step option (wait 15 minutes at step 120, skipped when resuming), so the crash happens at a known point.

Kaggle or Colab for a long run?

Kaggle, with Save & Run All. It runs in the background with the tab closed, and the weekly GPU quota is visible, so you know in advance whether a three-hour run fits. Free Colab disconnects idle sessions and its limits aren't shown. A closed-tab run on Kaggle confirmed it. The Hub checkpoints protect a run on either platform.

Say it "I treat free GPUs as machines that will vanish. Notebooks hold no logic; code is in Git, data and checkpoints are on the Hub, and resume is one flag. I tested it by killing a run on purpose, and when the first test didn't crash where I intended, I added a deliberate pause so the drill was repeatable."

6 · Local development setup

  • Postgres 16 with pgvector in Docker (pgvector/pgvector:pg16), one database for both the store's tables and the help-center vectors. One system instead of a separate vector database keeps operations simple at this scale.
  • Port 5433, not 5432. The laptop already ran a system Postgres on 5432; the container maps to 5433 rather than fighting it. Small, but the kind of thing that wastes an hour if undocumented.
  • Health check with pg_isready, so scripts wait until the database accepts connections.
  • Python 3.12 pinned with .python-version; uv for environments.
  • Repo hygiene from day one: .gitignore excludes tokens, .env files, model weights, checkpoints and generated data; folders exist for db, kb, rag, agent, api, evals, serving, training, ui.

Later the eval database also moved to a managed Postgres (Neon), because a Kaggle notebook can't reach a laptop. Local Docker stays the source of truth and is copied across with pg_dump; the decision and its checks are in DESIGN.md.

7 · How the model produces a reply

Before training a model you should know exactly what text it sees and how it decides to stop. These experiments ran on a MacBook (MPS, float16) with Transformers; scripts and outputs are in notes/generation-experiments/.

The prompt is one long string

A chat model doesn't see "messages". The chat template turns them into text with special tokens:

<|im_start|>system
You are Nova, NimbusCart's support assistant.<|im_end|>
<|im_start|>user
Hi, where is my order 4417?<|im_end|>
<|im_start|>assistant        ← added by add_generation_prompt=True
<think>

</think>
                              ← the model writes from here
  • add_generation_prompt=True opens the assistant's turn. Without it nothing says whose turn it is: in testing, the model wrote the assistant line itself, skipped the empty think block and started reasoning.
  • Thinking is switched off by the prompt, not a setting: the empty <think></think> block. Training data must contain the same block, or training and serving formats differ.

8 · GPU risk tests and the vLLM fix

Everything later depends on four things working on the actual hardware: a Kaggle T4. Rather than discover a blocker weeks in, all four were tested in one session first. Each test had a pass condition and a fallback decided in advance, and a failing test got at most 60 minutes of fixing (versions, flags, dtype) before taking its fallback.

#TestResultEvidence / pre-agreed fallback
1Generate with Transformers on a T4PASS145 tokens in 13.2 s (11 tok/s); same correct tool call as on the Mac. Fallback: text-only Qwen3-4B/1.7B.
250-step Unsloth LoRA: train, save, reload, generatePASSLoss 1.60 → 0.58 in 165 s on 200 rows; the reloaded adapter changed the output. Fallback: text-only Qwen3.
3vLLM serves the base model, one parsed tool callPASS (after fix)get_order_status({"order_id": 4417}), 50 tok/s. Fallback: evals with Transformers/llama.cpp, serve on a bigger GPU.
4vLLM serves the adapter as a LoRA modulePASSOne server answered both the base model and nova-test. Fallback: merge the adapter into the base.

Debugging the vLLM failure

In the first run, vLLM never started. The report showed only RuntimeError: Engine core initialization failed. See root cause above. The notebook had kept only the tail of the log, so the first fix was to the test itself: keep full logs and extract root-cause lines.

  1. Read the full log. About 300 lines above the final error: vLLM had loaded the model and was running a dummy forward pass to measure memory. Qwen3.5's gated norm layer calls FlashInfer's gemma_rmsnorm, which FlashInfer compiles on first use for the GPU's architecture (sm75 for a T4).
  2. Find the first real error. Compiling worked; linking failed: /usr/bin/ld: cannot find -lcuda.
  3. Understand why. Kaggle's image has the GPU driver only as libcuda.so.<version> under /usr/local/nvidia/lib64, not registered with ldconfig, and the CUDA stubs folder is empty. The linker looks for a plain libcuda.so.
  4. Separate noise from cause. The log also said FlashAttention 2 needs compute capability 8.0+ and FlashInfer sampling needs more than 7.5. Both were logged as errors but weren't fatal: vLLM fell back automatically.
  5. Fix with an ordered plan, time-boxed. A second notebook tried, in order: (A) symlink libcuda.so to the driver and add it to LIBRARY_PATH; (B) A + --enforce-eager; (C) A without FlashInfer; (D) A with an older vLLM. It would stop starting attempts after 60 minutes. Attempt A worked first time, using 11 of the 60 minutes.

The fix is now a reusable script, serving/t4_libcuda_fix.sh, sourced before vllm serve on Kaggle.

Say it "I tested the four riskiest assumptions on the real GPU before building on them, each with a fallback agreed in advance and a 60-minute fix limit. vLLM failed with a generic error; the real cause was 300 lines up in the log: a linker couldn't find libcuda.so because Kaggle only ships the versioned driver file. 9 · Defending the design: interview questions

Why not just call GPT-4 (or any large hosted model) with a good prompt?

For a narrow, high-volume job, a large hosted model costs more per conversation, adds network latency, and sends customer data to a third party. It is also harder to control: a prompt shifts probabilities, it doesn't guarantee behaviour. A small model I host, with retrieval, tools and code-enforced rules, is cheaper, faster, private, and every hard rule holds regardless of the model.

Why RAG for policies instead of fine-tuning them in?

Policies change. With RAG, a change is a document edit that takes effect immediately, and the answer can cite the current text. In the weights, a change needs a training run, and the model may still mix old and new numbers with no way to check where an answer came from.

The base model already calls tools. Why fine-tune at all?

It handles the easy case: an order number given in the message. Fine-tuning targets the hard cases: no order number, several orders, when not to call a tool, confirming before a write, escalating, and tone. It also replaces long prompt instructions, which a 2B model follows loosely and which cost latency on every turn.

Why is "only show customers their own orders" in code, not the prompt?

Because it must hold 100% of the time. A prompt is followed most of the time, and an attacker can try "ignore your instructions". The tool layer only ever queries the signed-in customer's rows, so even a fully compromised model can't leak another customer's order.

Why an 8K context when the model supports about 262K?

Memory, speed and accuracy. Each token in context costs GPU memory (KV cache), so a smaller window serves more conversations per GPU. Prefill time grows with prompt length, against a 3-second budget. And a 2B model finds facts less reliably in very long prompts. A support turn fits in 8K: system prompt, tools, recent history, four chunks and a reply.

Why does a long system prompt slow every turn?

The whole prompt is re-sent and re-processed in prefill on every request, until prefix caching lets the server reuse the part it has already processed. A system prompt that's 1,000 tokens longer is 1,000 extra tokens of prefill on every single turn.

Why non-thinking mode?

Measured: thinking used 3–11× the tokens and time on lookup turns and gave the same tool call. Without a tool it hit a 1,500-token cap and cut off. Support turns are lookups, not puzzles, and the latency budget is 3 seconds.

Why vLLM and not Transformers or llama.cpp?

vLLM decoded 4.5× faster than Transformers on the same T4, serves several conversations at once (continuous batching), has prefix caching, parses Qwen's tool calls into OpenAI JSON, and serves LoRA adapters next to the base model. llama.cpp was the pre-agreed fallback.

How do you make training reproducible on machines that disappear?

Stateless notebooks: code from Git, data and checkpoints on the Hub, settings in YAML, fixed seeds, pinned versions. Resume is a flag that pulls the last checkpoint. I proved it with a deliberate crash.

Tell me about a hard bug.

The vLLM start-up failure (section 8): a generic error, the real cause 300 lines up, a missing libcuda.so symlink. What I'd stress: I fixed the test first so it captured root causes, separated fatal errors from logged-but-harmless ones, and ran an ordered, time-boxed list of fixes instead of trial and error.

What would you do differently?

Capture full logs in every automated test from the start. Check stop tokens and the chat template before anything else on a new model. Validate training data for template artefacts like {{…}} before the first run, not after.

10 · Limits, open questions, glossary

Known limits and open questions

  • Cost is still an estimate. $5 per 1,000 conversations assumes $1/hour and 200 conversations/hour; it needs measured throughput on the chosen host.
  • Two-tool-call turns are over budget (p95 3.60 s against 3 s). Options: fewer passes per turn after fine-tuning, a shorter prompt, or a faster GPU.
  • All pass marks except the code-enforced ones are placeholders until the baseline eval of the untrained model.
  • Escalation is trained, not counted. If evals show missed escalations, a code backstop gets added.
  • English only, including Indian English. Hinglish is out of scope until there is training data for it, and an unscored probe measures the gap.
  • The T4 is an old GPU. Fast attention kernels need newer hardware, so production serving will likely use an L4/A10-class GPU.

Glossary

TermPlain meaning
LoRAFine-tuning that trains small add-on matrices instead of all 2B weights. The adapter is a few MB, and the base model stays unchanged.
AdapterThe saved LoRA weights. vLLM can serve several next to one base model (--lora-modules).
RAGRetrieval-augmented generation: search documents at answer time and put the relevant text in the prompt.
Tool callThe model outputs a structured request (function name + arguments); code runs it and returns the result.
Chat templateThe rule that turns a list of messages into the single string, with special tokens, that the model reads.
EOS / stop tokenThe token that means "turn finished". If generation doesn't stop on it, the model keeps writing.
Prefill / decodePrefill reads the whole prompt in one pass; decode then writes one token at a time. Long prompts make prefill slow.
KV cacheStored intermediate results for tokens already processed, so each new token doesn't re-read the whole prompt. It uses GPU memory per token.
Prefix cachingReusing the KV cache for a prompt start (like the system prompt) shared across requests.
p95 latency95% of replies are at least this fast. It describes the slow tail customers notice, not the average.
TemperatureHow random the next-token choice is. Low means consistent; high means varied.
vLLMA high-throughput inference server with batching, prefix caching, tool-call parsing and LoRA serving.
UnslothA library that makes LoRA fine-tuning faster and lighter on memory.
pgvectorA Postgres extension that stores embeddings and searches by similarity, so retrieval lives in the same database as orders.
Hub checkpointA training save pushed to Hugging Face, so a new machine can resume where the old one stopped.
