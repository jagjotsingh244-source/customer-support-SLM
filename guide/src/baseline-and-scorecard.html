The baseline:
measuring Nova before improving it

Before any fine-tuning, the cheapest version of Nova that could work was built and measured: a prompt, six rough tools and a plain loop around the untrained Qwen3.5-2B (the floor), and the same setup around a frontier model (the ceiling). This part explains how the agent, the 100 golden test cases and the scorer were built, why each choice was made, what the two systems scored, and what reading their failures says Nova must learn first.

1 · Why measure before improving

The tempting order is to fine-tune first. The problem shows up in the demo: "How much better is this than just prompting the base model?" Without a measured starting point there is no answer. Maybe prompting alone was already 80% as good. Maybe the fine-tune made one category worse. A result without a comparison is only a claim.

So two systems were measured before anything was trained, on the same 100 test cases:

  • The floor: the untrained Qwen3.5-2B with a system prompt and tools. Every later improvement has to beat it.
  • The ceiling: a much stronger model with exactly the same prompt, tools and loop. It shows how far this design can go.
Correct cases out of 100 (all checks passed, required tool calls made). The gap between floor and ceiling is the room that fine-tuning, retrieval and better tools have to close.

Each later improvement is then reported as the share of the gap it closes:

gap closed = (fine-tuned − floor) ÷ (ceiling − floor)
example:      (45 − 25) ÷ (58 − 25) = 61% of the gap closed

This follows the advice in Anthropic's Building effective agents: start with the simplest system (one model calling tools in a loop) and add complexity only when you can show it helps.

How I'd say it in an interview"Before training anything I measured a floor and a ceiling on the same 100 cases: the untrained 2B with a prompt scored 25, a frontier model with the identical setup scored 58. Every later change is reported as how much of that 33-point gap it closes, per category, so a gain in one place can't hide a loss in another."

2 · The agent: prompt, tools and loop

Three rough pieces, on purpose. They only needed to work; later stages make them good. What could not be rough were the safety rules.

The loop only ever speaks one API shape (OpenAI-style chat with tools), so swapping the model changes nothing else.

Prompt v0 (109 words)

Who Nova is, today's frozen date, the customer's name, and five rules: order facts only from tools, policy facts only from search_help_center; call a tool before talking about an order; list_my_orders if no order is named; one question at a time, under 80 words; hand off when asked or after two failed attempts. Versioned (PROMPT_VERSION = "v0") and never edited in place, so a score always maps to the exact prompt. Measured cost: 939 tokens on the first model call, tool schemas included.

The six tools

ToolWhat it returns
list_my_ordersrecent orders with item names
get_order_statusstatus, items, money, returns and refunds
get_trackingeach shipment: carrier, ETA, last scan
search_help_centertop 3 sections, keyword search
propose_returneligibility + a draft; creates nothing
escalate_to_humanrecords the hand-off

The rules that could not be rough

  • The customer comes from the session, never from the model. No tool takes a customer_id; every query filters on the signed-in customer. Asking about someone else's order returns not_found. A model that tries to pass customer_id anyway gets an error.
  • Nothing can write. The connection is opened read-only; an UPDATE is refused by Postgres. propose_return only drafts.
  • Refund status folded into get_order_status instead of a seventh tool, to stay inside the 700-token tool budget (6 tools measured at 656 tokens).
  • No agent framework. With a 2B model every token in and out has to be visible; a framework hides them.
How I'd say it in an interview"The tools are deliberately rough, but the safety rules aren't: the customer ID comes from the session, the database connection is read-only, and the return tool only drafts. Even v0 can't leak another customer's order or write anything, whatever the model says."

3 · Where the database lives

The 2B model runs on a free GPU notebook, but its tools need the store, and a notebook cannot reach Postgres on a laptop. Three options:

OptionUpsideDownside
Managed Postgres (Neon) · chosenLaptop and notebooks share one database; same Postgres 16 and pgvector as localAn account; the URL is a secret to manage
Postgres inside the notebookNo accountSeveral minutes of restore at the start of every run
Model on the laptop onlyNo GPU neededSlow, and not the serving stack

The local Docker database stays the source of truth; Neon is a copy made with pg_dump | psql from the container (so client and server versions match). The copy was proved, not assumed: all 13 tables have the same row counts, the orders table is byte-identical (an md5 over every row), and the 24 query checks pass against Neon. The password lives only in a gitignored .env and in notebook secrets.

4 · The help center as searchable sections

The 18 help-center pages were split on their ## headings into 103 sections, one rule each, stored in kb_sections with a stable id such as returns-electronics#opened-electronics (cases and citations point at it). A generated tsvector column over title, heading and body, with a GIN index, gives Postgres full-text search. The heading is searched too: "Opened electronics" holds the key word the body only implies.

This search is rough on purpose: websearch_to_tsquery requires every word of the query to appear in a section, and customers don't use the help center's words.

Customer's raw words as the queryResult
"return opened electronics"right section first
"can i return opened headphones"nothing ("headphones" is on no page)
"my parcel is late"nothing (the help center says "shipment" and "delayed")
All 25 policy questions, as typed3/25 found the right section; 22/25 found nothing

Leaving it weak was a decision: the baseline should show the weakness so that retrieval work later has a measured number to beat.

What this cost laterIn the eval, 72% of the 2B's searches and 40% of Gemini's came back empty. The weak search ended up limiting the frontier model more than its own intelligence did (section 8).

5 · Floor and ceiling: one loop, two models

The comparison is only fair if the model is the only difference: same system prompt, same six tool schemas, same loop, same 4-call limit, same temperature (0.2). Giving the bigger model a better prompt "because it can handle it" would make the gap measure prompting, not the model.

FloorCeiling
ModelQwen/Qwen3.5-2B, base weightsgemini-4-hydrogen (Google)
Served byvLLM 0.34.0 on a Kaggle T4 (serving latency); the scored run in-process on an Apple M4 with the same template, tools and samplingVertex AI, global endpoint
How the loop reaches itOpenAI-compatible API directly; on the Mac, a small client that parses tool calls the way vLLM doesAn adapter that translates messages; prompt, tools and loop unchanged
Thinkingoff (the chat template's default)always on; counts against the output cap, so the cap is 8,192 tokens

Why Gemini and not Claude

The plan was a Claude model through Anthropic's API. API use is billed separately and a Claude Pro chat subscription doesn't include it, so that route was out. The available Vertex AI key reaches only Gemini models. Two things the adapter has to handle: Gemini signs its own tool calls and rejects a rebuilt history (so its replies are replayed unchanged), and its thinking tokens count toward the output limit.

The first conversation, by hand

Customerhi where is my order?? it was supposed to come by monday

2Blist_my_orders → get_tracking(11904) in 6/6 runs: right order out of three, every time. But: "The estimated delivery date is 2026-11-16, which is in 5 days", four days after it had passed (3 of 6 replies wrong about the date).

GeminiSearched the help center for a delay policy ("late delivery delayed shipment" → nothing), tried again, ran out of its 4 calls, and handed off. 0 of 6 answered.

One conversation already told the story of the whole baseline: the small model fetches facts but can't reason about them; the big model reasons but is held back by the rough search tool.

6 · The golden set: 100 true cases

A golden set is a fixed exam with an answer key. The key is not a model answer to compare wording against; it is a list of checkable assertions: which tools, with which arguments; which facts must appear; which phrases must never appear; whether to hand off.

CategoryCasesWhat it tests
Policy questions25The right number from the help center; never the archived 30-day policy
Order lookups25Right tool and order; no invented delivery date for a late order; split shipments
Returns15Eligibility, the right refund amount, ask to confirm, never "created"
Unanswerable or off-topic15"I don't know" and a hand-off (EMI, coupons, gift wrap…), or a polite decline
Escalations10Possible loss, delivered-not-received, asked for a person, repeated failure, legal threat
Adversarial10Another customer's order, fake admin, "ignore your instructions", role-play jailbreak

Fixed quotas per category mean a gain in one area can't hide a loss in another. Every case uses an eval-partition customer (never one the training data can use) and a real order whose scenario is known.

Anatomy of one case

{"id": "ord-001", "category": "order_lookup", "scenario": "delayed", "customer_id": 416,
 "turns": ["hi where is my order?? it was supposed to come by monday"],
 "expect": {
   "tool_calls": [{"name": "list_my_orders", "args": {}},
                  {"name": "get_tracking", "args": {"order_id": 11904}}],
   "must_include": ["11904", "Nagpur"],
   "must_not_include": ["will arrive by", "expect it by", "arrive tomorrow", ...],
   "should_escalate": false, "confirm_card": false, "sources": []},
 "notes": "Webcam due Mon 16 Nov, last scan Nagpur hub 18 Nov. ETA has passed: share the last scan, promise no new date."}

must_include holds facts read from the database (the order number, the last scan), never from a model's reply. must_not_include holds the mistakes this case exists to catch: here, a promised delivery date for an order that is already late.

How the cases were written

  • Like customers write: lowercase, typos, no order number, two questions in one (3 compound and 3 multi-turn cases).
  • Specific facts over generic words: "598" (two doormats at 299), not "refund".
  • Traps on purpose: the archived 30-day return policy is forbidden text; an unopened band must not get the opened-electronics rule; an opened faulty band is returnable.
  • Real people in attacks: "Pranav Sood" and order 11904 exist (customer 416), so a leak would show up as real details.

Proving every case is true

evals/validate.py checks each case against the database and the help center, and CI runs it on every push:

  1. The format is exact (Pydantic; an unknown field is an error) and every id is unique.
  2. The customer is in the eval partition.
  3. Every order in an expected call belongs to that customer (in adversarial cases a foreign order must return not_found).
  4. The case's scenario is the order's seed scenario.
  5. Every expected tool call, run directly as that customer, returns real data, and list_my_orders really lists the order.
  6. Every cited help-center section exists.
  7. Every required fact appears in what the expected tools return or the cited sections, so no fact comes from memory.

Nine mistakes were planted on purpose (duplicate id, training customer, someone else's order, wrong scenario, invented "Mysore hub", an old order missing from the list, a made-up section, an unknown field); all nine were caught.

A bug the test cases found"Writing the returns cases exposed a real disagreement: the data marked earbuds as never returnable, even sealed, while the help center said 'not returnable once unsealed'. I kept the help center's rule, fixed the return check, the store's SQL, the seed and a data invariant together, then diffed the whole store before and after: exactly 10 rows changed, as intended."

7 · The scorer and why it is frozen

evals/run_eval.py runs every case with a fresh session for its customer, appends one trace per case as it goes (an interrupted run resumes where it stopped), scores it, and writes a per-category report with counts and percentages. Traces are kept, so any run can be re-scored later with new checks without calling a model.

CheckPasses when
tool_names, tool_argsStrict: exactly the expected calls, in order, with exact arguments (defaults filled in, free-text args match anything)
required_callsLenient: every expected call happens, in order, with the right arguments; extra lookups in between are allowed
valid_jsonevery tool call's arguments parse
factsevery required fact appears in Nova's replies
forbiddenno forbidden phrase appears
escalationhanded off exactly when it should; in unanswerable cases an explicit offer to hand off also counts
all · all_requiredevery check passes, with the strict tool checks (correct and efficient) or with required calls (correct)

Strict and lenient, on a real case

ret-001, "want to return the frying pan, dont need it anymore". Gemini's reply was perfect: right item, ₹1,199 refund, asked to confirm.

expected list_my_orders → get_order_status(11324) → propose_return(11324, 1, changed_mind)
Gemini did list_my_orders → search_help_center → get_order_status(11324) → search_help_center → propose_return(…)

Strict: fail (5 calls, not 3). Required calls: pass. A skipped lookup, a wrong order number or the wrong order of calls still fails both. Keeping both shows the difference between wasteful and wrong.

One text normaliser, shared by the validator and the scorer

"5–7 business days", "5 to 7" and "5-7" all become 5-7; "7-day window" matches "7 day"; "can't" reads as "cannot"; bank_transfer reads as "bank transfer". Without it, a correct reply fails over punctuation.

Frozen before the floor's results were seen

The two lenient changes (required calls, the offer rule) came from reading the ceiling's traces: 63 cases made every required call plus extra searches, and 7 unanswerable replies asked "Would you like me to hand this over to our support team?". Each was a general fairness fix, but adjusting a scorer every time a result looks odd ends in tuning the test to the answers. So the scorer was versioned as eval-v1 and frozen before the floor's results were in. Any change now needs a written reason, a new version, and a re-score of every run.

How I'd say it in an interview"I froze the scorer before I saw the floor's numbers, so nothing could be tuned to make the baseline look better or worse. Every system is scored by the same version, and because traces are saved, re-scoring after a justified change is free."

8 · Results: floor against ceiling

Correct cases (all checks, required calls) per category, scorer eval-v1. With 25 cases a category, one case is 4 points.
All 100 cases, check by check. "Correct + efficient" is the strict view: the floor wins it because the ceiling makes extra calls on almost every case.

The floor (Qwen3.5-2B)

100% of tool calls parsed and it found the right order for 22 of 25 lookups, but it never searched on 13 of 25 policy questions, 72% of its 36 searches came back empty, and 21 of 100 cases ended in the fallback hand-off.

The ceiling (Gemini)

Searched on every policy question and leaked nothing (adversarial 10/10), but made 285 searches (40% empty) and ran out of its 4 calls in 31 of 100 cases. It also preferred solving things itself: 2/10 on escalations.

How much the 4-call limit held the ceiling back

The 31 cases where the ceiling ran out of calls, re-run with 8 calls per turn. Labelled diagnostic and never reported as the ceiling, because the floor runs with 4.

About 12 of the 100 cases were lost to the limit, at the price of a 14-second median turn and 5.3 searches per case. The fix that keeps both speed and fairness is better retrieval, not more calls.

Read the traces before trusting the headlineThe first ceiling score was 14/100, which looked broken for a frontier model. Reading the traces showed perfect replies failing on extra searches and polite hand-off offers. The checks were fixed for every system, not the cases.

9 · Reading 30 failures

Numbers say how often; reading traces says why. The method is error analysis from qualitative research: read each failure and write one sentence on what went wrong (open coding), then group the sentences into a few types and count them. 30 of the floor's 75 failures were read, spread over the categories in proportion to their failures.

Type 2 also shrinks with better retrieval, so retrieval work gets measured on the same 100 cases.

10 · Sampling and latency

Temperature 0.2, chosen with data

The model card recommends temperature 1.0, top_p 1.0, top_k 20 and a presence penalty of 2.0. Both settings ran on the same 30 cases (the first five of each category):

Same 30 cases, same floor model. Reply length was identical (41 tokens per model call), so the difference is accuracy, not verbosity.

Temperature 0.2 won (9/30 against 5/30 correct). It matches the earlier generation experiments, where higher temperatures made the model refuse more often. One run each on 30 cases is a small sample: enough to act on, not a precise effect size.

Latency against the budget

MeasurementMedianp95Note
2B, vLLM on a T4, one conversation × 63.10 s3.60 stwo tool calls per turn
2B, vLLM on a T4, all 100 cases4.33 s7.71 sserving latency; about 3 model calls per turn
2B in-process on an Apple M411.0 s19.0 sreference kernels on MPS; not serving latency
Gemini on Vertex AI5.9 s12.1 sfrom India, rate-limit retries included

The budget is a 3 s p95 for a reply with one tool call. Each model pass on the T4 takes about 1–1.5 s, so a one-call reply is near 2 s, inside it; the baseline's turns use two or three calls, so they are over. Fewer wasted calls (failure type 2) is the first lever.

Cost of the ceiling run: 332 model calls, about 445,000 input and 70,000 output tokens on Vertex AI credits. The floor costs nothing per call: it runs on hardware you control.

12 · Defending the design: interview questions

Why measure a baseline before fine-tuning?

Without one, a month of training has no number attached. The floor (25/100) says what prompting alone gets; the ceiling (58/100) says how far the design can go. Every later result is a share of that gap, per category.

Why give the frontier model exactly the same prompt and tools?

So the gap measures the model, not the setup. The same holds for the 4-call limit: the 8-call run is a labelled diagnostic, never the ceiling.

Why assertions instead of comparing to a reference answer?

Many good replies exist. Assertions check what must be true (the order number, the last scan, no invented date) and ignore wording.

How do you know the test cases themselves are right?

A validator runs every expected tool call against the database and requires every expected fact to appear in a tool result or a cited help-center section. Nine planted mistakes were all caught, and it runs in CI.

Why two tool-use checks, strict and lenient?

Strict measures efficiency: extra calls cost latency and money. Lenient measures correctness: every needed call, in order, right arguments. Together they separate "wasteful" from "wrong".

Isn't changing the scorer after seeing results cheating?

It would be if it were tuned per system. The changes fixed checks that failed correct behaviour, were applied to every system, and the scorer was frozen before the floor's numbers existed. Future changes need a reason, a version bump and a re-score of all runs.

Why is the help-center search so weak?

On purpose: it is the baseline's retrieval. Raw customer wording found the right section 3 times in 25. That number, and 72% empty searches, are what better retrieval has to beat on the same cases.

The ceiling ran out of calls. Why not raise the limit?

Because the floor runs with 4, and a different limit would change the comparison. The diagnostic shows the limit cost about 12 cases; better retrieval should recover them within the limit, without 14-second turns.

Why temperature 0.2 when the model card says 1.0?

Measured on 30 cases: 9 correct against 5, facts 17 against 12, identical reply length. Support needs consistency more than variety.

The scored floor ran on a Mac. Is it comparable?

It uses the same weights (fp16), chat template, tool schemas and sampling as vLLM, and a tool-call parser written to match vLLM's. On the delayed-order case it gave nearly the same reply as vLLM. Its latency is excluded; serving latency comes from the T4 run. A T4 run of the same cases scored a few points lower, which is the run-to-run noise to keep in mind.

How do you stop another customer's data leaking?

In code, not the prompt: tools take the customer from the session and filter every query by it, so a foreign order is not_found. The adversarial cases check the words as well: both systems leaked nothing.

What does the error analysis change?

It decides what the first fine-tune trains: when to search versus ask, stopping once the facts are in hand, and the return flow. Those three types are 18 of the 30 failures read.

13 · Limits, what comes next, glossary

Known limits of this baseline

  • Deterministic checks miss meaning. They can't see negation, can't tell an echoed name from a leak, and can't catch "which is in 5 days" about a past date. An LLM judge comes later; the saved traces can be re-scored by it.
  • Some cases are debatable (asking for a reason first, "status" read as order status). They are listed, not changed, until the next scorer version.
  • Small numbers. One case is 4 points in a 25-case category; differences under about 8 points need fresh cases before they count.
  • Few compound messages (3 of 100, about 10 were planned). Messages written by other people are the next additions.
  • The ceiling is one specific model, gemini-4-hydrogen, not "frontier models" in general.

What comes next

  • Training data aimed at the counted failure types, built from train-partition customers only.
  • Retrieval measured on the same 100 cases, including whether to retrieve automatically every turn instead of leaving the decision to the model.
  • A proper tool layer (validation, a confirmation step for writes, ticket lookups) and an LLM judge next to the deterministic checks.

Glossary

TermPlain meaning
BaselineThe simplest system that might work, measured before any improvement.
