1 · What this part was for, and the result

The baseline (Part 3) gave Nova a deliberately rough help-center tool: Postgres full-text search where every word of the query had to match. It came back empty in 9 of the 11 policy cases where the 2B model searched, so the model answered refund and return questions from what it remembered, which is the internet's usual numbers, not NimbusCart's. This part replaced that tool with real retrieval, and measured each piece separately so a bad answer could be traced to the layer that caused it.

The order of work. Retrieval was scored on its own before any answer was generated, and the answer step was scored after, on the same golden cases as the baseline.

How I'd say it in an interview"I treated retrieval as its own system with its own test set: 97 labelled queries, scored by recall@3 before any answer was generated. That is how I found that hybrid search, the default for support bots, lost to plain vector search on this help center, and that editing six sections helped more than a model four times larger. End to end, the new tool returns the right section 8 times out of 11 instead of once, and when it does the small model gets the facts right. The remaining failure is that the model searches in only a third of policy questions, and that is a behaviour problem for training, not a retrieval problem."

2 · The pipeline in one picture

Two paths share one table. Offline, whenever a page changes, the pages are cut into chunks, checked, embedded and loaded. Online, the model decides to search, writes its own query, and gets back at most three labelled sections it can cite. Nothing in the online path touches the customer's raw message: the model writes the query, which turned out to matter for how retrieval should be measured (section 5).

The whole path. Offline, pages become checked, embedded chunks; online, the model writes a query, the tool returns up to three sections above the cutoff, and every reply is checked against what the tools returned.

3 · Chunking: one rule per section

The help center was written for this moment (Part 2): 18 pages, one rule per ## section, one term per idea, a version and an effective date in each page's front matter. So the chunking decision was mostly already made: a section is the unit a customer question is about, small enough for a 2B model to read the one rule it needs and big enough to keep an exception next to the rule it changes.

One chunk. The path line is embedded with the body, so a one-line rule still says what it is about; the ID is what Nova cites and what the golden cases name. (Body abridged.)

Why not fixed-size windows

A 256-token window would cut "Opened electronics can be returned only if faulty" away from "within 7 days", or glue a refund rule to an unrelated shipping rule. Overlapping windows patch the first problem by duplicating text, and produce IDs that mean nothing to a reader. Sections give clean boundaries and citable IDs for free.

Why the path line goes into the embedding

Many sections are one sentence. "You can return unopened electronics within 7 days of delivery" never says "return window"; its path, Returning electronics › Return window, does. Embedding the path with the body gives every chunk its topic words without editing the text.

All 104 chunks. Counted with the 2B model's own tokenizer, because these tokens are what the chunks spend of its context. No section came near the 400-token split threshold.

Two decisions about short chunks

  • Twelve one-line chunks were kept. Each is a single sharp rule, the best possible unit for retrieval and citation. Merging them by length would have blurred the rule and broken the IDs the golden cases cite. Length alone does not say whether a chunk is useful.
  • Two pointer-only chunks were rewritten. Sections that said only See "Split shipments". would fill a top-3 slot with nothing; they now state their rule and keep the reference.

A section over 400 tokens would be split at paragraph boundaries, with the first part keeping the section's ID so old citations still resolve. None needed it; the largest chunk is 120 tokens.

How I'd say it in an interview"The pages were written one rule per section, so I chunked by section: the boundaries are semantic, the IDs are human-readable, and a citation points at exactly one rule. I put the page title and heading on the first line of each chunk, because many rules are one sentence and never repeat the words a customer uses for their topic."

4 · Where the chunks live: pgvector in Postgres

The chunks sit in a kb_chunks table in the same Postgres database as the orders (local Docker for development, Neon in the cloud), with the pgvector extension for embeddings and a generated tsvector column for full-text search.

DecisionChoiceReason
Vector storepgvector in the existing Postgres104 rows. A separate vector database would add a service, a second copy of the data and a sync job, for no measured gain. Full-text and vector search also run side by side in one SQL query

Embedding columnUntyped vector plus embedding_modelLets models with 384 and 768 dimensions be compared in one table; the model name makes a mismatch detectable
Model checkEmbedder.check_index at connectQuerying bge-small vectors with a MiniLM query returns confident nonsense with no error; the check turns that into a refusal

How I'd say it in an interview"I kept vectors in the Postgres database the agent already uses. At about a hundred chunks an approximate index buys nothing and costs accuracy, so search is an exact scan. The one thing I guard hard is the embedding model: the table records which model wrote the vectors, and the tool refuses to search with a different one, because that failure is silent otherwise."

5 · Measuring retrieval before any answer

An end-to-end answer can fail for many reasons: the model did not search, searched badly, got the wrong section, or got the right one and misread it. To separate them, retrieval got its own test set and its own score before any answer was generated.

SetSizeWhere it comes from
questions.jsonl60The first turn of the 25 golden policy cases; 20 rewritten in customers' own phrasing (kb/_customer_words.md); 15 verbatim Bitext questions with typos or slang
model_queries.jsonl37The first query each model actually wrote for a golden policy case in the baseline runs (12 from the 2B model, 25 from Gemini)
unanswerable*.jsonl10 + 12Questions the help center cannot answer (gift wrap, EMI, price match…), used only for the cutoff (section 9)

How the labels work

Labels were written from the chunk text before any search ran, so they could not be fitted to a method. Each question has one or more answer groups: a group lists every chunk that answers that part on its own (the cash-on-delivery refund rule appears on three pages, so its group has three), and any one of them counts. A two-part question needs a hit from each group.

The two numbers

recall@3: the deciding number

The share of questions with an answering chunk in the top 3. Nova reads exactly three results, so a right answer at rank 4 is as useless as no answer. This is the number every choice was made on.

MRR: the tie-breaker

Mean of 1 / rank of the first answering chunk (top 10). It rewards putting the answer first, which matters when the model reads the first result most carefully.

Why two sets, and why the second matters moreThe tool never sees the customer's message. The model rewrites it into keywords: "return pickup time", "awaiting bank details refund". Raw customer messages, typos included, are the harder test; the 37 model-written queries are what the tool actually receives in production. A method that is good on one and bad on the other would be a trap.

Noise floor: with 60 and 37 questions, one question is 1.7 and 2.7 points. Differences of one or two questions are not findings.

How I'd say it in an interview"I scored retrieval on its own with recall@3, because the model reads three results and nothing else matters. And I scored it twice: on customer messages, and on the queries the models actually wrote in earlier runs, because in a tool-calling agent the model writes the query. The labels were written from the page text before any search ran, so I could not tune the labels to the method."

6 · Vector, full-text or hybrid

Five methods, one table, one embedding model. Hybrid search (vector and keyword results merged with reciprocal rank fusion, k = 60, top 20 of each) is the usual recommendation for support search, so it was the expected winner.

Same table, same embedding model (bge-small), five ways to search. Hybrid never beat plain vector search, and the any-word version lost 10 customer messages to filler words.

What the misses showed

  • Full-text needing every word almost never matches: it returned anything for 3 of 60 customer messages. That is exactly why the first tool kept returning [] in the baseline.
  • Full-text matching any word matches the filler. "used the bluetooth speaker once… want to give it back" ranked Coming back to a resolved ticket first; "i cant track my reimbursement" returned three shipment-tracking chunks. Fused into hybrid, that noise pushed right answers out of the top 3 on 10 messages and fixed 1 ("why was i charged 49 extra", where the exact number matters).

Why hybrid does not pay here

Hybrid's strength is exact tokens: order numbers, product names, model numbers, rare words that embeddings blur. In Nova, order numbers go to the order tools and never to the help center, the help center names no products, and the pages use one term per idea. Keyword search has nothing rare to catch. The hybrid code and its evaluation stay in the repo, to rerun if the help center ever gains product names or model numbers.

How I'd say it in an interview"Hybrid is usually right for support search, so I tested it rather than assumed it. Here it never beat plain vector search, and the any-word version lost ten messages to filler words like ‘back’ and ‘track’. The reason is the content: order numbers go to the order tools and the help center has no product names, so keyword search has no rare tokens to find. If that changes, the comparison is one command."

7 · Choosing the embedding model

Three embedding models, vector search, no query prefix. Blue: 60 customer messages; orange: 37 model-written queries. The model four times larger was worse on customer messages and 2.3 times slower.
  • bge-small-en-v1.5 leads on customer messages (0.83), ties on model queries (0.95), and costs about 6 ms a query on a laptop CPU. Embedding all 104 chunks takes 0.4 s.
  • MiniLM is faster but misses more paraphrases: 0.40 against 0.53 on the Bitext questions.
  • bge-base ranks model queries better (MRR 0.92 against 0.85) but is worse on customer messages and 2.3 times slower. At this size the embedding model is not the bottleneck.

The query prefix: off

bge's model card suggests prefixing short queries with an instruction (Represent this sentence for searching relevant passages:) and calls it optional for v1.5. It reordered 33 of the 60 top-3 lists, so it does something; it just did not help: the same 0.83 on questions and one query worse on model queries (0.92). Embedder defaults to no prefix, and --prefix reruns the comparison.

How I'd say it in an interview"I compared three embedding models on my own labelled set rather than a public leaderboard. The small bge model won on customer messages and tied on model queries at a third of the latency of the base model. I also tested the query instruction the model card recommends: it changed rankings but did not improve recall, so it is off and the comparison is reproducible with a flag."

9 · The cutoff: when to return nothing

Vector search always returns its three nearest chunks, even for "can you gift wrap my order". Handing a 2B model three unrelated sections invites it to answer from them. So the tool drops every chunk below a similarity cutoff and, when none is left, says No help-center page matches. Offer to connect a teammate.

Below 0.70 a retrieved chunk answers the question less than a third of the time; above 0.80, three times in four. Scores on their own cannot separate right from wrong: answering and non-answering top chunks overlap from 0.64 to 0.87.

The overlap is the hard part: on the 60 questions, the top chunk scores 0.60–0.93 when it answers and 0.64–0.87 when it does not. A cutoff cannot be read off the answerable questions; it has to come from questions that have no answer. Two sets were built for that: 10 unanswerable customer messages and 12 queries the models wrote for unanswerable golden cases.

Raising the cutoff empties more unanswerable queries and, past 0.68, starts losing answerable ones. 0.68 is the highest value that keeps every answerable model query (0.95) and empties all 12 unanswerable ones.

Cutoff 0.68 (MIN_SCORE in agent/tools_v1.py) is the highest value that keeps every answerable model query and empties every unanswerable one. It was chosen on model queries because that is what the tool receives; on raw customer messages the same cutoff would cost 11 points of recall, which is why the cutoff lives in the tool and not in the retrieval evaluation.

The margin is thinThe highest-scoring unanswerable query ("out of stock restock availability") scored 0.668, just under the cutoff. The constant carries a comment saying so: recheck it whenever the help center, the embedding model or the query style changes.
How I'd say it in an interview"Similarity scores do not separate right from wrong chunks here; the ranges overlap almost completely. So I chose the cutoff on questions with no answer: 0.68 is the highest value that keeps every answerable model query and returns nothing for all twelve unanswerable ones. I know the margin is thin and wrote that next to the constant, because it is a number that silently goes stale."

10 · The new tool and prompt v1

The model sees one change: search_help_center now returns up to three labelled sections, each with an ID to cite and the policy's effective date, plus a short instruction. An empty result says what to do instead of returning nothing.

{"results": [{"id": "returns-electronics#return-window",
              "title": "Returning electronics › Return window",
              "text": "You can return unopened electronics within 7 days of delivery.",
              "effective_date": "2026-10-01"}],
 "note": "Cite results as [kb:<id>]. If none answer the question, say so."}

{"results": [], "note": "No help-center page matches. Offer to connect a teammate."}
  • Compact on purpose. A whole result costs 256 Qwen tokens at the median and 342 at most, so the budget for retrieved text dropped from 2,000 tokens to 1,000: room for three searches in one turn.
  • Effective dates travel with the text, so an answer can say "since 1 October" when a customer quotes an older rule.
  • The order tools did not change. One variable at a time: any change in answers comes from search.

Prompt v1 adds one rule to v0: cite every policy fact as [kb:<id>], for example [kb:returns-electronics#opened-electronics], and when the search returns nothing, say the help center does not cover it and offer a teammate. Prompts and tools are versioned (--prompt v0|v1, --tools v0|v1) and every run records both.

How I'd say it in an interview"The tool returns three short sections with IDs and effective dates, about 250 tokens, so the small model reads exactly what it needs and can cite it. When nothing clears the cutoff, the tool tells the model what to do instead of handing it an empty list. I changed only the search tool and one prompt rule, so the results compare cleanly with the baseline."

11 · Grounding checks on every reply

"Grounded" was made measurable instead of hoped for. agent/grounding.py runs on every final reply inside the agent loop and logs its findings in the trace; the scorer recomputes them from saved messages, so every earlier run was rescored too (no older metric changed).

Every number in a reply must appear in a tool result from earlier in the same conversation, and every [kb:id] must be a section a search returned. The red line is adapted from a real reply (pol-010) where the 2B model never searched; there both 7 and 10 were flagged. Here 7 passes only because the card line mentions it: numbers are matched one at a time.
  • Numbers. Each number in the reply must appear among the numbers of tool results Nova was given earlier in the same conversation (order lookups and help-center results alike). "1,299" and "1299.00" normalise to the same value. A number that is true, or that sits elsewhere in the help center, or that the customer typed, does not count.
  • Citations. Each [kb:id] must be the ID of a section a search actually returned. Digits inside a citation are not claims.
  • Logged, never fixed silently. The check measures; it does not rewrite replies. Blocking belongs to the guardrails, later.

What it found on day one

The agent loop had been writing tool results with json.dumps defaults since the first baseline, so the 2B model read "1\u20133 business days" and "\u20b949" instead of "1–3 business days" and "₹49". Gemini receives tool results as parsed JSON and never saw the escapes, so part of the baseline gap between the two models was formatting. One argument fixed it (ensure_ascii=False), and old traces are decoded before checking.

What it cannot see

  • Dates are checked one number at a time. "Your return window ends on October 7, 2026" passed, because 7 and 2026 each appear in some tool result. Dates need to be matched whole; that is a guardrail task.
  • Customer numbers are flagged on purpose. "rather than 30 days" repeats the customer's own claim and is flagged, because the customer's words are not evidence. That costs a few false positives, each one easy to read in the report.
How I'd say it in an interview"I made grounding a number. Every reply is checked: each number must appear in a tool result from that conversation, and each citation must be a section the search actually returned. It runs in the loop and in the scorer. On its first day it found that the small model had been reading escaped JSON since the baseline, which the stronger model never saw. I also know its gap: dates are matched digit by digit."

12 · Old policies: archive and versions

The hardest grounding test is a customer quoting a rule that used to be true. NimbusCart's returns policy changed on 1 October 2026 (electronics 30 → 7 days, pickup 3–5 → 1–2 days); the old page lives in kb/_archive/ with superseded_by in its front matter.

Kept out of the index twice

kb/_archive/ is skipped by path, and the chunker also refuses any page whose front matter has superseded_by. An archived page copied back into kb/ stops the load instead of competing with the current rule at search time.

Five old-policy golden cases

The customer quotes the archived rule ("30 days to return anything", "pickup in 3–5 days", "refund within 7 days of pickup") and Nova must give and cite the current one. They test retrieval, reading and the nerve to correct the customer.

The five cases where the customer quotes an archived rule (“30 days for everything”, “pickup in 3–5 days”). Same tools and prompt for the last three rows; only the model differs.

The ceiling run (2026-11-25_ceiling-old-policy) corrected the customer in all five and cited the right section each time. Three of its five fail the strict tool-sequence check, all for extra calls (a second search, an order lookup for the headphones), not wrong ones. Its one grounding flag is the customer's "30 days" quoted back. The ship gate asked for these five to pass on the ceiling model: they do, so the 2B model's 3/5 is a model gap, not missing content.

How I'd say it in an interview"Policies change, so every result carries its effective date and the old page lives in an archive the index refuses to load, checked twice. 15 · Defending the design: interview questions

Why chunk by section instead of fixed-size windows?

The pages were written one rule per section, so the section boundary is a semantic boundary. Fixed windows would cut a rule from its exception or merge two unrelated rules, and their IDs would mean nothing. Sections also give citable, human-readable IDs, and none was long enough to need splitting (largest: 120 tokens).

Some chunks are one sentence. Isn't that too small?

For retrieval, a single sharp rule is ideal: the embedding is about one thing and the citation points at one rule. The risk is that a one-line rule lacks topic words, which the path line (page › heading) fixes. I rewrote only the two chunks that were pointers with no rule.

Why pgvector instead of a vector database?

104 rows. A separate database adds a service, a copy of the data and a sync job for no measured benefit, and keeping it in Postgres lets vector and full-text search run in one query against one table.

Why no HNSW index?

An approximate index trades a little accuracy for speed on large tables. At 104 rows an exact scan is instant and returns true nearest neighbours, so the evaluation measures the embedding model, not index approximation. I'd add one past tens of thousands of chunks.

Why recall@3?

Because the tool returns three results and the model reads three. A right answer at rank 4 is invisible to it. MRR is the tie-breaker for how high the answer lands.

Hybrid search is the standard for support bots. Why did you drop it?

I tested it: it never beat vector search on recall@3, and the any-word version lost 10 customer messages to filler words while fixing one. Hybrid wins on exact rare tokens, and this help center has none: order numbers go to order tools, there are no product names, one term per idea. The code and evaluation stay, so it is one command to recheck if the content changes.

Why bge-small over a bigger embedding model?

On my labelled set it led on customer messages and tied on model queries, at 6 ms against 14.5 ms. The four-times-larger bge-base was worse on customer messages. Page edits moved recall more than model size did, so the model was not the bottleneck.

The model card recommends a query prefix. Why is it off?

I measured it: it reordered 33 of 60 top-3 lists but gave the same recall on questions and one query worse on model queries. Off by default, and a flag reruns the comparison.

Why measure on model-written queries, not just customer questions?

In a tool-calling agent the model writes the query, usually clean keywords. Those 37 real queries are the production distribution; raw messages with typos are a harder stress test. I chose methods on both and the cutoff on the production one.

How did you pick 0.68, and isn't it fragile?

From unanswerable questions, because answering and non-answering scores overlap too much to read a threshold off answerable ones. 0.68 is the highest cutoff that keeps every answerable model query and empties all twelve unanswerable ones. Yes, the margin is thin (0.668), so it is documented as something to recheck when the pages, the model or query style change.

Why edit the pages instead of improving the retriever?

Reading the misses showed most were content problems: the page used different words, or said nothing (no page mentioned exchanges). Six edits beat a larger model. In a real company that is also the cheapest fix, and it improves the help center for humans too.

How do you stop the model from hallucinating policy?

Three layers: the tool returns only sections above the cutoff and says so when nothing matches; the prompt requires a citation for every policy fact; and a grounding check traces every number and citation in every reply to tool results, logged in the trace and scored. The evaluation showed all invented numbers came from not searching, which points the fix at behaviour.

Your grounding check flagged a correct answer. Isn't it broken?

It flags numbers the customer typed, on purpose: the customer's words are not evidence. That costs a few false positives that are easy to read, against never letting a repeated wrong number pass. Its real gap is the other way: dates are matched one number at a time, so an invented date can pass. That is listed for the guardrails.

Retrieval works but the model searches in a third of cases. Was this wasted?

No, it located the problem. Before, I could not tell whether bad answers came from search or the model. Now search is measured at 0.95 on real queries, and the remaining failures are tool choice: list orders first, then run out of calls. That is a training-data problem, which is why the next fine-tune trains on tool-using conversations.

How do you handle policy changes?

Each page carries a version and an effective date, which travel with every result. Superseded pages live in an archive that is excluded by path and by a front-matter guard, so they cannot compete at search time. Five golden cases quote the old policy and check that Nova corrects it with a citation; the ceiling model does in five of five.

Why not add a reranker?

I didn't measure one, so I won't claim it would or wouldn't help. On model queries recall@3 is already 0.95, and the remaining misses are raw typos the agent never sends. A cross-encoder adds latency to every search. It becomes worth testing if the help center grows or recall drops.

What would you do differently?

Build the model-query set first: it is the production distribution and it would have saved time on the raw-message set. Make the index loader keep embeddings by default. And match dates whole in the grounding check from the start.

16 · Limits, what comes next, glossary

Known limits

  • Small, self-labelled sets: 60 and 37 questions, labelled by me. One question is 1.7 and 2.7 points.
  • The cutoff margin is thin (0.668 against 0.68) and depends on the model's query style.
  • Raw typos still miss; retrieval relies on the model rewriting messages into keywords.
  • Dates are checked number by number in the grounding check.
  • No reranker, no query expansion; neither was measured.
  • Reloading chunks without --model clears the embeddings.

What comes next

  • Behaviour: search first on policy questions, cite what was retrieved, never state a policy number without a search. The three hallucinations in this part are the training signal for the next fine-tune.
  • Prompt: scope the "list orders first" rule to order questions, the likely cause of the wasted calls.
  • Guardrails: match dates whole, and decide which grounding failures block a reply.
