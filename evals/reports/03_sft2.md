# SFT-2: training on tool-using conversations

SFT-2 is two LoRA adapters (r 16, alpha 16, the seven attention and MLP projections) over the frozen Qwen3.5-2B,
each trained for one epoch (593 steps of 16 examples) on `nova-sft2-mix-v1`: 9,485 model calls taken from
conversations a teacher model had inside the real agent loop, filtered hard (`notes/synthetic-conversations/`).

- **SFT-2a** starts from the base model, learning rate 2e-4. Adapter `123jagjot/sft2a-r16-lr2e-4-traj_v1`.
- **SFT-2b** continues from SFT-1 (Nova's voice, no tools), learning rate 1e-4. Adapter
  `123jagjot/sft2b-r16-lr1e-4-traj_v1`.

Training runs in `training/runs/sft2a-r16-lr2e-4-traj_v1/` and `training/runs/sft2b-r16-lr1e-4-traj_v1/`;
settings in `training/configs/sft2a.yaml` and `sft2b.yaml`; both trained on one A100-80GB on Modal
(`training/modal_train.py`), about 15 minutes each.

**In one line:** both adapters use tools again, and correctly: on the 107 golden cases, correct answers rose from
**29 (base) and 11 (SFT-1) to 69 (SFT-2a) and 67 (SFT-2b)**, with no tool-call format errors and fewer model calls
than the base model. SFT-2a is the one served: tied overall, better on returns, and it does not depend on SFT-1.

## The checks

| Check | Data | Result |
|---|---|---|
| 1. Loss | 266 validation examples from whole held-out conversations | 2a: 0.530 → 0.237; 2b: 0.878 → 0.245; neither turned up |
| 2. Probes during training | Five fixed requests, every 100 steps | Both 5/5 from step 100 to the end |
| 3. Golden set with tools | The 107 golden cases, full agent loop | **Base 29, SFT-1 11, SFT-2a 69, SFT-2b 67** |

### 1. Loss

Step 0 is the starting point: the base model for 2a (LoRA's B matrix starts at zero), SFT-1 for 2b.

| Step | 0 | 100 | 200 | 300 | 400 | 500 | 593 |
|---|---|---|---|---|---|---|---|
| SFT-2a | 0.530 | 0.338 | 0.313 | 0.280 | 0.246 | 0.239 | **0.237** |
| SFT-2b | 0.878 | 0.314 | 0.302 | 0.275 | 0.250 | 0.247 | 0.245 |

SFT-1 starts further from this data than the base model does (0.878 against 0.530): what it learned from Bitext
(offer to check, ask permission, never call) is the opposite of these targets. It was unlearned within the first
100 steps, and from there the two curves run together; SFT-2b ends slightly higher. Starting from SFT-1 bought
nothing measurable. This fits Biderman et al. (2024), "LoRA Learns Less and Forgets Less": a low-rank adapter
moves the model only a little, so a second LoRA stage on very different targets mostly overwrites the first rather
than building on it.

### 2. Probes

Five requests, generated greedily at every evaluation with Nova's serving prompt, empty state and the six tools
(`training/sft.py`, `TOOL_PROBES`):

| Request | Right first step | Base (2a, step 0) | SFT-1 (2b, step 0) | Both, steps 100 to 593 |
|---|---|---|---|---|
| "thanks!" | a reply | `list_my_orders` | reply | reply |
| "are you a bot?" | a reply | a reply, then `list_my_orders` | reply | reply |
| "where is order 11904" | a call | `get_tracking` | "Would you like me to look up your order?" | `get_tracking` |
| refund time (policy) | a call | `search_help_center` | asks permission | `search_help_center` |
| "thanks" after an answer | a reply | `escalate_to_human` | reply | reply |

The base model calls a tool for everything; SFT-1 calls a tool for nothing; both SFT-2 adapters tell the two
apart from step 100.

### 3. Golden set

Run `evals/runs/2026-11-25_golden-{base,sft1,sft2a,sft2b}`: all four systems on one vLLM 0.34.0 server on Modal
(the adapters served as LoRA modules), prompt v2, tools v2, the state block and history trimming as served,
temperature 0.2, at most 4 model calls per turn, scorer `eval-v3`. Each system ran against its own copy of the
database, so no run could clear another's return proposals between cases. (The runs record
"+uncommitted changes": an unrelated edit to the Gemini adapter, a path these runs do not use.)

Correct = `all_required`: every required call, the right facts, nothing forbidden, the right hand-off.

For scale: the Gemini ceiling scored 58/100 in the first baseline (`00_baseline_ceiling.md`). That run used prompt
v0, the first tools and an older scorer, and cannot be repeated with these settings while the Google project is
blocked, so it is a reference point, not a like-for-like comparison.

**SFT-2a against SFT-2b.** Eight cases only 2a gets right, six only 2b; 69 against 67 is not a difference at this
size. Two places differ in kind:

- **Returns, 7 against 3.** In three return cases SFT-2b proposed the return straight after a help-center search,
  without looking at the order first, and once called the proposal "created". SFT-2a looks the order up, then
  proposes.
- **Unanswerable, 10 against 12.** SFT-2b more often offers a teammate when it cannot answer.

SFT-2a is chosen: returns are the flow that writes to the database, its loss is lower, and it stands on its own
without SFT-1 underneath.

## What SFT-2a still gets wrong

All 38 failed cases read one by one, each tagged with its main failure:

| Failure | Cases | Examples |
|---|---|---|
| Help center searched but misread, or "the help center does not cover" a rule it does state | 9 | old-001, pol-022, pol-025 (the 15-day window and the warranty rule were there); pol-021 looked up an order's refund instead of reading the payment-failure section |
| Wrong lookup or a required call skipped | 8 | `get_order_status` where tracking was needed (ord-008, ord-016); cancellations answered without looking at the order (ord-018, ord-024). Two are arguably right answers the scorer counts as wrong: ord-015 answers "delivered" from the status, ord-025 makes both calls in the other order |
| A hand-off that was needed, not made | 6 | esc-001 (no movement for over a week: "it has not been lost"), esc-003, esc-010 (third message, threatening court), ret-015 (offers a hand-off but never calls it) |
| Out of scope declined flatly, with no search and no teammate | 5 | una-004 (gift wrap), una-006 (restock date), una-007 (store pickup), una-010 (courier's number), esc-007 (care number) |
| Hand-off or the fixed fallback reply instead of an answer | 5 | ret-003, ret-007 (handed off instead of proposing the return); pol-014 and esc-005 used up four calls and ended on "Let me connect you with a teammate." |
| Return flow wrong | 3 | ret-010 worked out a return deadline itself; ret-011 proposed a return, then said it could not be returned; ret-009 asked instead of proposing |
| Missing item in a split delivery: tracking number not given | 2 | ord-012, ord-014 |

Three of these trace back to the data, not to the model:

- **Hand-offs for delays.** The teacher was told a late parcel is not a lost one, and the filters rejected any
  late parcel offered a hand-off. The student learned it too well: "not lost" even after a week without
  movement, where the golden set expects a hand-off.
- **Out of scope.** The no-tool chats taught a short, polite decline without a tool; the golden set wants a search
  and an offered teammate for these. Those chats should end with the offer.
- **The fallback reply.** Four calls in a turn still end on the fixed hand-off line, and two cases reached it.

## Data shortfall

The plan was 2,000 conversations that pass every check. 1,006 passed (of 3,270 generated), so the mix leans on
4,772 salvaged leading steps of conversations failed only by the fact-check judge, and on 105 Bitext rows instead
of the planned 20% share (only rows right without a tool and free of SFT-1's habits qualified). The categories
with the fewest clean conversations are the ones that fail most here: hand-offs for real problems, and
out-of-scope requests.
